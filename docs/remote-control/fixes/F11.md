### Release signing and fleet migration
- Inventory every tablet before release. Pull the installed APK with `adb shell pm path com.example.webkiosk` and `adb pull`, then record its SHA-256 signing certificate with `apksigner verify --print-certs`; compare with the candidate and retained keystores. Record device ID, version and signer. An update needs the same signer or a valid signing lineage; package name and increasing version code must also match upgrade requirements. See [Android app signing](https://developer.android.com/studio/publish/app-signing) and [apksigner](https://developer.android.com/tools/apksigner).
- The present Windows CI passes no signing environment and generates `local_debug.keystore` on a fresh hosted runner. Tablets installed from different runs likely have different, unrecoverable keys unless the actual keys were saved; locally built tablets may have a persistent local key. Confirm from installed APKs, not artifact names. The current macOS CI expects a prebuilt APK; local macOS builds generate or reuse a local key.
- Custodian securely retains the matching production private key and an encrypted offline recovery backup, with restricted access and documented recovery ownership. Store the keystore as a protected CI secret (`KIOSK_KEYSTORE_B64`), decode to a restricted temporary file, set `KIOSK_KEYSTORE` to its path, and supply `KIOSK_KEYSTORE_PASS` and `KIOSK_KEYSTORE_ALIAS` as protected secrets. Clean up the file; never log or publish secrets. Restrict signing to trusted release jobs; untrusted builds use debug keys and cannot publish fleet artifacts. Release builds fail closed if material is missing, malformed or its certificate is not the approved fingerprint; never generate a release key automatically. Publish APK digest, certificate fingerprint, version and provenance with each release.
- Retain the old private key for a planned rotation: create and retain an APK Signature Scheme v3 signing lineage using `apksigner rotate`, sign with the appropriate old and new signers and lineage, and verify on API 35 and each supported older API before release. API 35 supports the v3.1 rotation path. A lineage cannot recover an already lost old private key. Treat compromise as a security incident and plan reprovisioning if a trusted transition is impossible.
- Both OS build wrappers invoke the same Gradle release configuration and signing inputs. Windows and macOS packaging consume the same approved, verified release APK; macOS CI must obtain that artifact from the trusted build and verify its digest and signer rather than expect a committed APK. Debug APKs are clearly labeled and never packaged for fleet release.
- USB setup uses `adb install -r` and checks exit status and output. On `INSTALL_FAILED_UPDATE_INCOMPATIBLE`, stop immediately, report the signer mismatch and direct staff to inventory/recovery; never uninstall the app or continue provisioning. Stop on every other install failure as well. A Device Owner cannot simply be uninstalled while active.
- If the installed signer is unrecoverable, schedule supervised, per-device reprovisioning: record device identity and required configuration, arrange recovery of any needed data and factory-reset protection credentials, revoke its old relay registration, and factory reset using the approved managed procedure. Install the approved signed APK on the clean device, provision Device Owner with the supported USB procedure, restore lock task allowlist and kiosk configuration, enroll a new device key with supervised approval, verify connectivity and kiosk behavior, and retire the old identity. Factory reset destroys the old app data and device key. Do not automate reset or silently uninstall as an upgrade fallback.

## Acceptance tests
- On a provisioned K11/API 35 with production-equivalent Device Owner and enrolled key, record version, signer, owner component, lock-task allowlist, active lock-task behavior and enrolled public-key fingerprint. Install a higher-version approved APK with `adb install -r`; verify success, same owner and allowlist, kiosk launch/lock-task behavior after reboot, and a fresh relay challenge signed by the **same** enrolled key. Confirm application data persists. Repeat for each deployed signer cohort or explicitly reprovision that cohort.
- Install a deliberately incompatible-signed higher-version APK through the manager: it reports failure, runs no uninstall or subsequent setup steps, and owner, allowlist and enrolled key still work. Exercise other install errors too.
- Verify release APK with `apksigner verify --verbose --print-certs`, compare fingerprint and digest to the approved record, and inspect both Windows and macOS packaged APKs. Missing or wrong CI secret fails release before publishing. Test any rotation on a provisioned tablet from the old signer, including a subsequent update and key continuity.
- On a designated test tablet, exercise the reset/reprovision procedure and verify new owner, lock task, new enrollment, and rejection of the revoked old identity. Record results before fleet rollout.
