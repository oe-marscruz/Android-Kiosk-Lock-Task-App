### 3.2 Tablet credential (device ↔ relay)
- **Supervised enrollment:** From a local support-only enrollment screen during USB setup, generate a new Android Keystore EC P-256 signing key. No credential is delivered by ADB, exported receiver, or app restriction. The tablet POSTs its DER SubjectPublicKeyInfo (SPKI) over HTTPS to the configured relay; the relay validates P-256 and creates a random 128-bit request ID and device ID, both lowercase hex, and a `pending` record expiring after 10 minutes. Rate-limit pending requests and cap their number. No remote-control privileges exist in `pending` or `approved`.
- The tablet displays the request ID and **SHA-256 of the exact DER SPKI**, as 32 uppercase hex byte pairs separated by colons, labelled `SHA-256`, in native support UI. The signed-in enrollment admin compares the entire request ID and fingerprint on the physical tablet with the desktop display and explicitly approves that exact pending record. The approval endpoint requires an admin session and records the admin, time, request ID and fingerprint in the audit log. Reject expired, changed, already approved or revoked records. Approval alone does not activate a key.
- **Key storage:** Attempt StrongBox using `setIsStrongBoxBacked(true)` when `FEATURE_STRONGBOX_KEYSTORE` is present. If unavailable or `StrongBoxUnavailableException` occurs, generate a fresh key without that flag; report the resulting `KeyInfo.getSecurityLevel()` as StrongBox, trusted environment or software to the admin. Other generation errors fail enrollment. Software fallback is visibly flagged for explicit admin approval. This local report is informational, not remotely verified attestation. Android Keystore keys are non-exportable; factory reset removes the key. See [Android Keystore](https://developer.android.com/privacy-and-security/keystore) and [StrongBoxUnavailableException](https://developer.android.com/reference/android/security/keystore/StrongBoxUnavailableException).
- **Proof and connection:** Each WSS connection starts unauthenticated. The tablet sends `device_auth_start{device_id}`. For an unexpired `approved` or `active` record, the relay returns `device_challenge{nonce}` with 32 cryptographically random bytes, base64url without padding. A challenge belongs to that socket, expires 60 seconds after issuance on the relay's monotonic clock, and is invalidated on disconnect. No other device traffic is accepted before authentication.
- Sign exactly these bytes: ASCII `CU-DENVER-KIOSK-DEVICE-AUTH` followed by one NUL byte, then four fields in order: `1`, relay audience, device ID, nonce. Each field is UTF-8 encoded and prefixed by its unsigned 32-bit big-endian byte length. Audience is the exact configured `DEVICE_AUTH_AUDIENCE` string, shared by tablet and relay, identifying this relay deployment; device ID is the lowercase hex string and nonce is the base64url string as transmitted. The tablet rejects an unexpected audience: `device_challenge` also includes `audience`, which must equal its configured value. Sign using ECDSA P-256 with SHA-256 (`SHA256withECDSA`); send the ASN.1 DER signature as unpadded base64url in `device_auth_proof{device_id,sig}`. Reject malformed encodings, wrong IDs, audience, signatures, expired or reused challenges. The relay atomically consumes the challenge on the first proof attempt, successful or not; retries require a new connection and challenge.
- **State:** `pending → approved` requires the physical comparison and admin approval. On valid proof, atomically transition `approved → active` and bind that socket; `active` reconnects require fresh proof. Approval expires with the pending request if no proof arrives within 10 minutes of creation. Only one active socket per device: a successful new connection closes the old one. An admin can transition any non-revoked state to `revoked`; persist a tombstone, invalidate challenges, close its socket, detach staff sessions and reject subsequent proofs. Serialize revocation with proof and routing so no command is accepted after revocation commits. A revoked key or device ID cannot be reactivated: supervised re-enrollment generates a new key, request and device ID. Key loss or reset also requires re-enrollment; an admin revokes the old record. Audit approval, activation and revocation.

### 4. Wire protocol amendment
- Replace device `hello{device_id, sig, app_version, caps}` with `device_auth_start{device_id}`, relay `device_challenge{audience,nonce}`, and `device_auth_proof{device_id,sig}` as specified in §3.2. After relay authentication success, the device sends `hello{device_id,app_version,caps}` and may send frames, acknowledgements and status. All control messages retain the §4 envelope.

Acceptance tests:
- Unit: fixed transcript and signature vectors verify byte lengths, UTF-8, DER and base64url; mutations to audience, ID, nonce, signature or socket fail. Check expiry at 60 seconds, replay, disconnect and concurrent proof attempts.
- Unit/integration: pending cannot connect; wrong fingerprint or ID cannot approve; expired approval cannot activate; valid proof activates atomically; concurrent revocation and proof never leave a revoked device connected or route a post-revocation command. Revoked key and ID cannot be reused; fresh enrollment succeeds. Exercise duplicate socket replacement and audit records.
- Emulator: supervised enrollment displays the full fingerprint matching independently hashed SPKI; admin approval and WSS proof succeed over a local HTTPS relay. Verify no enrollment bearer appears in an ADB command or broadcast and software fallback is shown.
- K11 checkpoint: verify support UI is reachable during supervised setup under lock task, physical fingerprint comparison, actual reported security level and reconnect; revoke while connected and confirm immediate disconnect and explicit re-enrollment. Confirm student WebView allowlist is unchanged.

Interfaces touched: `device_auth_start`, `device_challenge`, `device_auth_proof`, `hello`; `DEVICE_AUTH_AUDIENCE`; enrollment request and admin approval endpoints; device registry states `pending`, `approved`, `active`, `revoked`; native support enrollment screen.
