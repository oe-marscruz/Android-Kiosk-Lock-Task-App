### §§2 and 2.2 — tablet components and manifest

Replace `SupportApprovalActivity` with native views owned by the existing `MainActivity`; enrollment is another in-activity panel. Neither panel is an exported component. Add these declarations to the existing manifest (permissions under `manifest`, components under `application`):

```xml
<uses-permission android:name="android.permission.FOREGROUND_SERVICE" />
<uses-permission android:name="android.permission.FOREGROUND_SERVICE_SPECIAL_USE" />
<uses-permission android:name="android.permission.RECEIVE_BOOT_COMPLETED" />

<service android:name=".remote.KioskA11yService"
    android:exported="true"
    android:permission="android.permission.BIND_ACCESSIBILITY_SERVICE">
    <intent-filter>
        <action android:name="android.accessibilityservice.AccessibilityService" />
    </intent-filter>
    <meta-data android:name="android.accessibilityservice"
        android:resource="@xml/kiosk_a11y_service" />
</service>
<service android:name=".remote.RemoteAgentService"
    android:exported="false" android:foregroundServiceType="specialUse">
    <property android:name="android.app.PROPERTY_SPECIAL_USE_FGS_SUBTYPE"
        android:value="Maintains the outbound connection for attended kiosk support" />
</service>
<receiver android:name=".remote.BootReceiver" android:exported="false">
    <intent-filter>
        <action android:name="android.intent.action.BOOT_COMPLETED" />
    </intent-filter>
</receiver>
<receiver android:name=".remote.EnrollmentSetupReceiver" android:exported="true" />
```

The accessibility metadata is the XML in §2.2; only the system can bind through the required permission. The boot receiver accepts only `BOOT_COMPLETED`, after unlock; start the foreground service only when platform restrictions permit, and report unavailable on failure. The setup receiver accepts only the explicit action below and authenticates its sender; it has no intent filter and no manifest permission because shell does not hold an app signature permission. It never accepts credentials. `MainActivity` retains its existing launcher declaration. See [service declaration](https://developer.android.com/guide/topics/manifest/service-element), [special-use FGS](https://developer.android.com/develop/background-work/services/fgs/service-types#special-use), and [receiver declaration](https://developer.android.com/guide/topics/manifest/receiver-element).

A pending authenticated support request is delivered internally to the visible, resumed, focused `MainActivity`, which renders the named Allow/Deny panel above the WebView. No activity, notification, system overlay or background launch is used. If no eligible activity is visible, remain pending only until its deadline, then deny; never grant on resume automatically. Approval, banner and Stop are local native controls outside remote input; apply the existing session, visibility, invalidation and capture rules. Lock task constrains activity launches and allowlisted packages, while Android restricts background activity launches; updating the existing visible window avoids relying on either exception. See [lock task](https://developer.android.com/work/dpc/dedicated-devices/lock-task-mode) and [background activity starts](https://developer.android.com/guide/components/activities/background-starts).

### §3.2 and §7.1 — supervised USB enrollment entry

During attended USB setup, with the kiosk visible and debugging temporarily authorized, kiosk-manager sends no extras or secrets:

```sh
adb shell am broadcast -n com.example.webkiosk/.remote.EnrollmentSetupReceiver -a com.example.webkiosk.action.BEGIN_ENROLLMENT
```

On API 34+ the receiver checks `getSentFromUid()` equals `android.os.Process.SHELL_UID`, checks the exact action and absence of extras, and requires this app to be the active Device Owner. Reject unknown/invalid UID, all other callers, other actions and unsupported API levels. It signals the existing visible `MainActivity` in-process; no activity launch. Accept only while that activity is resumed and focused, otherwise fail and require staff to retry. Display a local enrollment panel with explicit Start and Cancel; block support and remote input throughout. The panel expires after five minutes, closes on focus loss, process death, cancel or completion, and is never restored automatically. Start generates the key and proceeds with §3.2's local full fingerprint and request-ID comparison and authenticated admin approval. Disconnect USB, disable debugging and revoke debugging authorizations after setup. The trusted authorized USB host is part of the supervised setup boundary; a person with authorized ADB can trigger the panel, but cannot supply a secret or bypass physical comparison.

A non-exported enrollment activity cannot be started by the shell UID with `am start`; exported activities need their own trustworthy authorization. A shell-UID-gated explicit receiver is chosen because [getSentFromUid](https://developer.android.com/reference/android/content/BroadcastReceiver#getSentFromUid()) supplies the sender identity or INVALID_UID; reject the latter and verify on K11. Activity launch identity is not generally available to the callee without identity sharing ([Activity API](https://developer.android.com/reference/android/app/Activity#getLaunchedFromUid())). Device Owner status alone authenticates the app, not the person or caller: a student-accessible DO button would also work for a student. A staff PIN could restrict a local button, but needs secure provisioning, recovery, rate limiting and protection against observation; it does not itself establish supervised USB. No student-facing trigger, WebView bridge, remote command or intent extra enters enrollment.

## Acceptance tests:

- Inspect the merged manifest on the installed build: names, exported states, binding permission, XML metadata, FGS type/property and permissions; test that an unprivileged app cannot bind the accessibility service or invoke internal services. Check the protected boot action after reboot and first unlock; record FGS start outcome and fail closed if unavailable.
- On the actual K11 with deployed G06 lock-task packages and feature flags, connect a staff session while MainActivity is visible. Verify pending panel, local Allow/Deny, named banner and Stop, no frames/input before approval, and immediate stop on focus loss or banner loss. Repeat with another activity visible, process recreation and timeout; no background activity appears and no approval survives.
- Under the same lock-task flags, run the exact supervised USB broadcast; verify sender UID, visible enrollment panel, local Start, fingerprint comparison and successful enrollment. Verify repeated, malformed, expired, background and non-shell broadcasts do not enter enrollment; verify a separate ordinary app cannot spoof shell UID, and a non-exported activity rejects shell `am start`. Test actual shell UID visibility on the fleet image: INVALID_UID or blocked delivery means setup fails and release is blocked, not a bypass.
- Close enrollment, disconnect USB, disable debugging and revoke authorizations; exercise student navigation, launcher, intent attempts and remote commands: no enrollment route or input to approval controls. Verify the unchanged domain allowlist. Record device build, lock-task flags, commands and outcomes.
