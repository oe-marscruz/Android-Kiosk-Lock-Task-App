# F05 — Duo MFA and step-up

Replaces/amends: §§2.1 (configuration bullet), 3.1 (steps 3–4), 3.3 (roles and wipe/exit bullets), 7 (P5 row), 8 (Duo question). Other text remains in place; reconcile §3.1 transaction binding with finding 4 and authorization with finding 6.

## Drop-in replacement text

### §2.1 configuration bullet
- Relay configuration (environment or protected config file; secret from environment or protected file only):
  - `OIDC_ISSUER`: exact HTTPS issuer, pinned per deployment. Discovery `issuer` and token `iss` must equal it exactly; obtain endpoints and JWKS only from that discovery document over TLS. Never discover from a token claim.
  - `OIDC_CLIENT_ID`, `OIDC_CLIENT_SECRET`, `PUBLIC_BASE_URL`.
  - `OIDC_ALLOWED_ALGS`: nonempty explicit asymmetric ID-token signing algorithm allowlist, restricted to algorithms advertised by the pinned issuer and verified by the implementation. Reject `none`, symmetric algorithms and unconfigured algorithms; no algorithm inferred from a token.
  - `OIDC_REQUIRED_AMR`: nonempty set of accepted MFA evidence values agreed with the tenant owner; a validated ID token's `amr` array must contain at least one. Missing, malformed or unaccepted evidence denies login and step-up. No permissive default.
  - `ROLE_GROUP_CLAIM`: optional exact claim name; `ROLE_GROUP_MAP`: explicit group-value-to-role mapping. Alternatively `ROLE_PRINCIPAL_MAP`: explicit `(issuer, subject)` to role mapping. Configure one source; missing or ambiguous mappings deny access. Roles are `viewer`, `operator`, `admin`; no email fallback or automatic role.
  - `DESTRUCTIVE_ACTIONS_ENABLED`: boolean, default `false`. Enabling requires recorded P5b evidence for this issuer, RP and policy; configuration changes affecting that evidence require disabling and re-verification. False denies `wipe` and `exit_kiosk` at relay dispatch regardless of role or client UI.

### §3.1 staff login — replace steps 3–4
3. The relay exchanges the code using the client secret and verifier. Validate the ID token signature with pinned-issuer JWKS and an allowed algorithm; exact `iss`, `aud` containing this client ID, `exp`, `iat`, nonce and nonempty `sub`. Reject a present `azp` unequal to the client ID; require matching `azp` when `aud` has multiple values. Apply bounded clock skew. Reject missing or unacceptable `amr` as configured; do not infer MFA from login success, `acr`, or a remembered session alone. Duo's [Generic OIDC guide](https://duo.com/docs/sso-oidc-generic) describes `amr` and `max_age=0`; its [SSO guide](https://duo.com/docs/sso) says remembered devices can inherit earlier AMR and bypass can omit it.
4. Key the principal by `(iss, sub)`. Resolve its role using the configured mapping; deny unmapped or ambiguous identities. Only then issue the one-time handoff code described below. The RP's tenant policy must enforce MFA and exclude bypass/skip paths; accepting an AMR value alone does not establish fresh MFA.

### §3.3 authorization — replace roles and wipe/exit bullets
- Roles: `viewer` can watch only. `operator` can watch, send touch input and use navigation. `admin` adds DPM commands. Resolve roles using §2.1, and enforce device scope and every operation at the relay.
- `wipe` and `exit_kiosk` are disabled unless `DESTRUCTIVE_ACTIONS_ENABLED` is true and P5b is recorded. Require desktop confirmation and a new, transaction-bound OIDC code flow with `max_age=0`, independent state, nonce and PKCE. Validate the ID token as in §3.1; require the same `(iss, sub)`, current admin authorization, accepted `amr`, and a valid `auth_time` no earlier than the step-up request (allow bounded clock skew), no more than 5 minutes old and not in the future beyond skew. Missing or unverifiable freshness denies the action. The Generic RP guide does not document `auth_time`; do not assume it exists. CU OIT must confirm both the claim semantics and that policy forces a new MFA challenge, including when a remembered device exists.
- On successful step-up, issue an opaque, server-side, single-use grant bound to principal, live session, device and exact action, expiring at the earlier of five minutes after `auth_time` or session expiry. Atomically consume it at dispatch after rechecking authorization, feature flag and confirmation; reject replay, mismatch, expiry, session revocation or policy change. Never pass Duo tokens to the desktop or tablet. Audit intent, denial and result without tokens or claims.

## Acceptance tests

- **Mock IdP:** valid signed token with configured issuer, algorithm, audience, nonce, subject, accepted AMR and mapped role succeeds. Reject wrong issuer/discovery issuer, unsigned or disallowed algorithm, bad signature, wrong audience, missing/wrong `azp` as applicable, expired token, wrong nonce, absent subject, absent/malformed/unaccepted AMR and unknown or ambiguous role. Same `sub` from another issuer cannot inherit a role.
- **Mock step-up:** verify `max_age=0`, independent transaction and matching principal; reject missing/stale/future `auth_time`, wrong session/device/action, role removal, revoked session and replay. Concurrent redemption dispatches at most once. With flag false, both operations fail even with a valid grant; toggling policy invalidates grants. Confirmation alone never authorizes dispatch.
- **P5a:** using local relay and trial tenant, capture sanitized evidence of successful login and `max_age=0` step-up, ID-token claim names/values and timing, and observe whether fresh MFA occurs with remembered device. Test bypass and missing/unaccepted AMR; verify denial. Exercise grant binding and replay with a harmless substitute; flag remains false. Missing `auth_time` or reused MFA is a failed step-up, not a workaround.
- **P5b:** repeat with CU RP and CU OIT witnessing/confirming policy and claim semantics; test remembered device, bypass/skip and unmapped user, and confirm they cannot bypass the checks. Record issuer/RP/policy version and sanitized results. Enable only after all evidence passes; test actual operations only on a designated disposable test device with explicit authorization.
