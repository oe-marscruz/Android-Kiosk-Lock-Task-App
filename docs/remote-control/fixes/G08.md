# G08 — Auth transport in deployment and tests

**Replaces/amends:** §2.1 Logging; §2.3 TLS and Packaging; §3.1 callback origin; §7 P5a; §7.2 TLS test.

## Drop-in replacement

### Relay access logs (§2.1)

Caddy and relay access logs never contain raw URLs, headers or bodies. Use this site-level Caddyfile block with the reverse proxy to `127.0.0.1:<port>`; retain the deployment's existing site address and proxy configuration:

```caddyfile
log {
    format filter {
        request>uri delete
        request>headers delete
        resp_headers delete
    }
}
```

This deletes the entire URI, including `/auth/start/<id>` and every query string, and all request and response headers, including Authorization, Cookie and Set-Cookie. Do not enable `log_credentials`; do not append raw URI or headers to logs. Caddy's encoder also supports `regexp` for a field, but whole-field deletion avoids path encoding and unknown query-key bypasses. Do not use the `uri` handler for log redaction: it changes the request sent to the relay. Configure runtime/error logs and all other sinks to avoid URLs, headers and exception dumps containing secrets; verify them separately. See [Caddy log directive](https://caddyserver.com/docs/caddyfile/directives/log).

Configure aiohttp `access_log_class` as a subclass of `aiohttp.abc.AbstractAccessLogger`. Its `log(request, response, time)` emits only an allowlisted route template or a constant `unknown`, method from a fixed allowlist, status and duration; never raw path, query, headers, body, exception text or `%r`. Map routes by the router's canonical template, not a substituted user path; fall back to `unknown` when unavailable. Sanitize application and error logs independently. See [aiohttp server reference](https://docs.aiohttp.org/en/stable/web_reference.html) and [access logger interface](https://docs.aiohttp.org/en/stable/abc.html).

### Desktop TLS (§2.3, §7.2)

One context factory creates `ssl.create_default_context(cafile=certifi.where())`, preserving `CERT_REQUIRED` and hostname checking. Pass its context to `urllib.request.urlopen(..., context=...)` or `http.client.HTTPSConnection(..., context=...)` for every relay HTTPS request, and to `websockets.asyncio.client.connect(..., ssl=context)` for WSS. No unverified retry or certificate-error bypass. The bundled certifi CA file is required in the frozen Windows artifact. Test-only CA injection uses the same factory and validation settings, with a separately supplied test CA bundle; production configuration cannot select it. See [websockets client](https://websockets.readthedocs.io/en/stable/reference/asyncio/client.html).

### Trial callback (§3.1, §7 P5a)

Run the relay and Caddy on the Arch dev box. Use `https://localhost:<port>/auth/callback` as the fixed `PUBLIC_BASE_URL` callback, Caddy `tls internal`, and install Caddy's local root in the actual browser's trust store. The desktop's trial-only certifi-derived bundle must additionally trust that root; the production bundle stays unchanged. Verify the browser and desktop both validate the localhost SAN; never disable validation. Trust is local to the trial and remove the root after it. Duo's [Generic OIDC RP documentation](https://duo.com/docs/sso-oidc-generic) requires the request URI to match a registered Sign-In Redirect URL; it does not explicitly promise localhost acceptance. Register the exact URI without a wildcard and verify acceptance and a complete browser round trip in the user-owned tenant before counting P5a as passed. The separate desktop handoff remains `http://127.0.0.1:<port>/cb` and is not Duo's redirect URI.

If Duo rejects localhost, use a temporary public hostname with an ACME certificate, resolving/routing to the local Caddy instance, and register its exact HTTPS callback. Keep the relay on loopback; restrict and remove temporary exposure after the trial. A local CA hostname is an alternative only if Duo accepts its exact URI and the browser and desktop trust its root. Do not substitute the OCI deployment for P5a.

## Acceptance tests:

- Validate and adapt the actual Caddyfile using the deployed Caddy version. Send requests with unique sentinel start IDs, arbitrary and duplicate query keys, Authorization, Cookie and Set-Cookie values, including encoded paths, errors and redirects. Inspect every Caddy access and runtime sink and relay access and error sink: no sentinel or raw URL appears; status and duration remain useful. Confirm the reverse proxy receives the unchanged URI. Exercise unknown routes and error paths.
- On Arch, run local HTTPS and WSS servers with a test CA (e.g. trustme or locally generated certificates). Through the real desktop HTTPS and WSS paths, a trusted valid SAN succeeds; untrusted issuer, expired leaf and hostname mismatch each fail before application data is sent. Repeat in Windows 10 and 11 test images against the packaged executable with the isolated test CA bundle, then confirm the normal artifact uses its bundled certifi trust store. No network fallback occurs.
- P5a: record exact Duo RP registration, browser trust, desktop trust and successful callback round trip against the local relay. Record rejection and use the documented fallback if localhost is disallowed. Remove trial trust and exposure afterward.
