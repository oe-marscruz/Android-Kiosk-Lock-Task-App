# Remote staff control protocol v1

Status: **P1a draft, freeze pending review.** Baseline: ARCHITECTURE.md v0.6 §2.1, §3.1–§3.4 and §4. Where this file and ARCHITECTURE.md disagree, ARCHITECTURE.md wins and this file is the bug.

The protocol is defined by these artifacts together:

| Artifact | Defines |
|---|---|
| `v1.schema.json` | Every JSON text message on the WSS hops, and the JSON header of a binary frame (`$defs/frame_header`) |
| `http-v1.schema.json` | Request and response bodies of the HTTP routes in §10 |
| `../../../relay/contracts.py` | Relay-internal contracts (§2.1) and the closed registries. The schema enums must equal them |
| `fixtures/valid`, `fixtures/invalid` | One or more examples per message type, and rejected inputs with the defect they show |
| `fixtures/scenarios` | Ordered message sequences for races. Data only; the harness arrives in P2/P3 |
| `../../../tests/test_protocol_fixtures.py` | CI check that all of the above agree (`.github/workflows/protocol.yml`) |

## 1. Change control

- The lead owns this file and both schemas. After the freeze, a change needs lead review, updated fixtures and coordinated consumers (relay P2/P3, `kiosk_remote/`, tablet agent).
- Every object in the schemas has `additionalProperties: false`, so **any** new field, message type, op, reason or code is a breaking change for an old receiver. v1 has no optional-extension mechanism. Such a change ships either as a coordinated v1 revision (all three components upgrade together, before the relay starts sending it) or as `v: 2`.
- v1 has no version negotiation. A peer that receives `v` other than `1` treats it as described in §4.

## 2. Transport

- One WSS connection per staff desktop and per tablet, both dialled out to the relay (Caddy :443 → aiohttp on loopback).
- **JSON messages** are WebSocket *text* messages: exactly one UTF-8 JSON object per message, no BOM.
  - Duplicate object keys are rejected. JSON Schema can't see duplicates, so every parser must use a duplicate-rejecting hook (for example `object_pairs_hook` in Python, a strict reader on Android).
  - Integers are JSON integers. `1.0` is not a valid `frame_id`.
  - `NaN` and `Infinity` are not JSON and are rejected by the parser, so every number that validates is finite.
- **Frames** are WebSocket *binary* messages (§7). They flow tablet → relay → desktop only.
- Messages larger than the WebSocket max message size (aiohttp default, 4 MiB) are closed by the transport.

## 3. Envelope and IDs

Every JSON message is `{"v":1,"type":<string>,"id":<string|null>, ...body}`. The body fields sit beside the envelope fields, not inside a nested object.

| `id` kind | Rule | Messages |
|---|---|---|
| request | Non-null string, `^[A-Za-z0-9_-]{1,64}$`, chosen by the sender, unique among that sender's outstanding requests on the connection | Every staff → relay message; relay → device `cmd`, `reserve`, `execute`; device → relay `device_auth_start`, `device_auth_proof` |
| reply | Echoes the request `id` exactly | `staff_ready`, `devices`, `attach_result`, `detach_result`, `lease_renew_result`, `logout_result`; `device_challenge`, `device_ready`; `reserved` |
| event | Must be `null` | Everything else except `error` |
| error | The offending request's `id` if it was parsed as a valid envelope id, otherwise `null` | `error` |

- The envelope `id` is used **only** to match a reply to its request. It is never a command identifier, a dedup key or an authorization input.
- `command_id` is a separate body field. The desktop chooses it, and it is carried unchanged on both hops. Dedup, terminal results and acks are keyed by `(attachment_id, command_id)`. Using the envelope `id` in place of `command_id` is schema-invalid (fixtures `invalid/id-as-command_id*.json`).
- `cmd_result` and `ack` are events (`id: null`): they are correlated by `command_id`, never by `id`.
- Wire IDs (`device_id`, `attachment_id`, `grant_id`, `reservation_id`, `request_id`) are 128-bit random lowercase hex. They are lookup keys, never credentials. Secrets (`token`, `step_up_id`, `status_secret`, nonces) are 256-bit base64url without padding.

## 4. Unknown and invalid input

Every v1 receiver validates each inbound text message against its **inbound direction** in `v1.schema.json` (`$defs/staff_to_relay`, `relay_to_staff`, `relay_to_device` or `device_to_relay`), not against the permissive root. A message that fails validation is never partially processed.

| Input | Relay receiving from staff or tablet | Desktop receiving from relay | Tablet receiving from relay |
|---|---|---|---|
| Not UTF-8, not JSON, duplicate key, not an object | `error{INVALID_MESSAGE}` with `id:null`, then close | Close; clear the viewer and disable input | Close; invalidate all attachments, grants and reservations |
| `v` is not `1` | `error{UNSUPPORTED}`, then close | as above | as above |
| `type` unknown for this direction | `error{UNSUPPORTED}`, then close | as above | as above |
| Unknown or missing field, wrong type, out-of-range value, unknown reason, unknown error code | `error{INVALID_MESSAGE}`, then close | as above | as above |
| Binary message from staff, from a tablet before `device_ready`, or with an unknown type byte | `error{INVALID_MESSAGE}` (unknown type byte: `UNSUPPORTED`), then close | Close | n/a (the relay never sends binary to a tablet) |
| Anything before authentication other than the handshake message | Staff: generic `error{UNAUTHENTICATED}`, close. Tablet: `error{DEVICE_AUTH_FAILED}`, close | n/a | n/a |

- **Fail closed means close.** Unknown input means the peers disagree about the contract, so the connection is not trusted for anything else. Closing releases the sender's attachments through the normal `disconnect` path (ARCHITECTURE §3.3).
- The desktop and tablet never answer the relay with an error for an invalid relay message; they close. A tablet may send `error` (with the request `id`) only for a relay request it parsed but cannot correlate, for example an `execute` on a connection with no matching command. Semantic command failures use `ack{ok:false}`.
- WebSocket close: protocol and auth violations use close code `1008` with an empty reason. Relay shutdown uses `1001`; an internal fail-closed condition (audit store or authoritative state unavailable) uses `1011`. Reasons are never put in the close frame.
- Unknown values inside known messages are never mapped to a default. In particular an unknown terminal reason is not shown as a generic message: the whole message is rejected.

## 5. Handshakes and lifecycle

**Staff.** Within 10 s of the WebSocket opening, the first and only pre-auth message must be `staff_auth{token}`. The relay replies `staff_ready{session_id, display_name, expires_at}` with the same `id`. Any other message, a bad token or the timeout gets `error{UNAUTHENTICATED}` with `id:null` and a close; the token is never echoed and never read from a URL or query string. When the session ends while connected, the relay sends `session_ended{code}` (`SESSION_EXPIRED`, `UNAUTHENTICATED` for revocation, or `DISABLED_BY_POLICY` when `STAFF_LOGIN_ENABLED` is turned off) and closes.

**Tablet.** `device_auth_start{device_id}` → `device_challenge{audience, nonce}` → `device_auth_proof{device_id, sig}` → `device_ready{device_id}`, then the tablet sends `hello{device_id, app_version, caps}` and periodic `status`. `sig` is the DER `SHA256withECDSA` signature over the transcript in ARCHITECTURE §3.2, base64url without padding. Every failure is the same `error{DEVICE_AUTH_FAILED}` and close.

**Attachments.** Transitions are in ARCHITECTURE §3.3. On the wire:

- Every acquisition sends `attach_open{attachment_id, mode, lease_ms}` to the tablet. `display_name` is required for `mode:"kiosk"` (it is the banner text) and forbidden for `mode:"status"`.
- Every accepted `lease_renew` sends `lease_renewed{attachment_id, lease_ms}` to the tablet **before** any work that depends on the renewal is forwarded, and `lease_renew_result{…, expires_at}` to staff.
- Every release that the tablet did not originate sends `detach{attachment_id}` to the tablet.
- The tablet reports `support_pending` when its approval prompt is visible, `support_granted{grant_id, remaining_ms}` on Allow, `support_stopped{reason}` on grant end, and `attachment_expired{reason:"lease_expired"}` when its local lease runs out. The relay forwards these to the owning staff socket as `support_pending`, `support_granted{grant_id, expires_at}`, `support_stopped{reason}` and `attachment_ended{reason}`.
- A staff-initiated `detach` is answered with `detach_result`; no `attachment_ended` follows for it.
- Late or duplicate tablet events for a released attachment are ignored under the device lock and never touch a replacement (`fixtures/scenarios/delayed-detach-after-replacement.json`).

**Timers on the wire.** The relay never sends absolute times to a tablet: `lease_ms`, `deadline_ms` and `ttl_ms` are relative and the tablet starts them from `elapsedRealtime()` at receipt. Staff receive absolute `expires_at` values (RFC 3339 UTC) for display only.

**Schema maxima.** v1 caps these fields at the ARCHITECTURE §2.1 default limits: `deadline_ms` and `ttl_ms` ≤ 5000 (`CMD_DEADLINE_S`), `lease_ms` ≤ 60000 (`LEASE_IDLE_S`), `remaining_ms` ≤ 300000 (`GRANT_MAX_S`), swipe `ms` ≤ 5000. Deployment config may lower these limits. Raising one above the cap is a protocol revision.

## 6. Commands

Staff send `cmd{command_id, device_id, attachment_id, op, args, grant_id?, frame_id?, generation?, step_up_id?}`.

| Op | `args` | Binding fields | Relay → tablet |
|---|---|---|---|
| `tap`, `long_press` | `{x, y}` | `grant_id`, `frame_id`, `generation` required | `cmd` |
| `swipe` | `{x1, y1, x2, y2, ms}` | `grant_id`, `frame_id`, `generation` required | `cmd` |
| `kiosk_back`, `kiosk_home`, `reload_kiosk`, `lock_now`, `reboot` | `{}` | `frame_id`, `generation` forbidden; `grant_id` when the attachment is kiosk, absent on a `status_admin` status lease | `cmd` |
| `wipe` | `{}` | `grant_id` and `step_up_id` required; `frame_id`, `generation` forbidden | `reserve`, then `execute` (never `cmd`) |
| `navigate`, `enter_kiosk`, `exit_kiosk` | `{}` | as the row above | **never** |

- Coordinates are numbers in [0, 1] relative to the content-rect crop of the bound frame. All four binding IDs (`attachment_id`, `grant_id`, `frame_id`, `generation`) are carried unchanged on both hops.
- `step_up_id` appears only on a staff `wipe` and never on any relay → tablet message.
- **Reserved ops.** `navigate`, `enter_kiosk` and `exit_kiosk` are valid op names in the staff schema so the relay can recognise, audit and deny them, rather than closing the socket as for an unknown op. The relay always answers `error{DISABLED_BY_POLICY}` with the request `id`, whatever the role, grant or configuration, audits the denial, forwards nothing and does not record the `command_id`. Their `args` must be `{}`, so no URL or target can ever be carried. They are **not** valid in relay → tablet `cmd`; a tablet that receives one closes (§4). See `fixtures/scenarios/reserved-op-denied.json`.
- **Plain wipe.** The relay never sends `cmd{op:"wipe"}`; it is schema-invalid on the relay → tablet hop, and a tablet that receives one closes without dispatching.
- **Relay → tablet `cmd`** adds `deadline_ms` (the remaining relay budget at write time) and drops `device_id` and `step_up_id`.

**Admission vs. result.** A command gets exactly one of these:

1. **Admission rejection**: `error{code}` with the cmd's request `id`. Nothing is queued and nothing is recorded under `(attachment_id, command_id)`, so a later retry with the same `command_id` is evaluated afresh. Codes: `FORBIDDEN`, `DISABLED_BY_POLICY`, `LEASE_BUSY`, `LEASE_REQUIRED`, `GRANT_REQUIRED`, `ATTACHMENT_STALE`, `GRANT_STALE`, `OVERLOADED`, `DISCONNECTED`, `DUPLICATE_ID_CONFLICT`, `INVALID_MESSAGE`.
2. **Terminal result**: once admitted, exactly one `cmd_result{device_id, attachment_id, command_id, state, error}` with `id:null`.

| `cmd_result.state` | `error` | Meaning |
|---|---|---|
| `ok` | `null` | Definitive positive ack |
| `failed` | any code | Dropped at the writer before any send (denial, release, audit failure), or a negative ack other than `RESERVATION_EXPIRED` |
| `rejected_expired` | `DEADLINE_EXCEEDED` or `RESERVATION_EXPIRED` | The relay deadline ran out before the send, or the tablet rejected the reservation as expired |
| `outcome_unknown` | `OUTCOME_UNKNOWN` | A send was attempted and no definitive ack was recorded before the attachment was released or the socket closed. Never replayed |

- A duplicate cmd with identical content re-sends the recorded `cmd_result` if the command is terminal, and is otherwise ignored (the single result arrives later). Different content under the same `(attachment_id, command_id)` gets `error{DUPLICATE_ID_CONFLICT}`.
- The tablet reports each dispatched command with exactly one `ack{command_id, attachment_id, ok, err}` (`id:null`). `ok:true` requires `err:null`; `ok:false` requires an `err` from `contracts.ACK_ERROR_CODES`. A tablet that refuses a `reserve` (lease, grant or policy) answers with `ack{ok:false}` for that `command_id`, not `reserved`.
- A late ack after `OUTCOME_UNKNOWN` was reported is audited only (`fixtures/scenarios/late-ack-after-outcome-unknown.json`).
- **Wipe.** `reserve{command_id, op:"wipe", attachment_id, ttl_ms}` → `reserved{command_id, attachment_id, reservation_id}` (echoing the `reserve` id) → `execute{reservation_id, command_id, attachment_id}` → `ack`. The step-up is consumed only at the execute writer commit. See `fixtures/scenarios/wipe-expiry-during-audit.json` and `release-between-reserve-and-execute.json`.

## 7. Binary frames

A frame is one WebSocket binary message:

```
offset  size  field
0       1     frame_type   0x01 = JPEG frame (the only v1 type)
1       4     header_len   unsigned 32-bit big-endian, 2 ≤ header_len ≤ 1024
5       N     header       UTF-8 JSON object, exactly header_len bytes, valid against v1.schema.json $defs/frame_header
5+N     rest  jpeg         baseline or progressive JPEG of the content-rect crop, ≥ 1 byte, starting FF D8
```

`header` is `{"attachment_id","grant_id","frame_id","generation","width","height"}`. `width` and `height` are the JPEG's pixel dimensions (1–8192). Capture time is **not** in the header; it stays tablet-local metadata (`request_uptime_ms`).

**Why this encoding.**
- The type byte comes first so a receiver can reject an unknown frame kind before parsing anything else.
- The u32 big-endian length prefix is the same convention as the device-auth transcript (ARCHITECTURE §3.2), so the tablet uses one length-prefix helper.
- A length-prefixed header makes the JPEG boundary explicit. A delimiter scan could be confused by JPEG bytes, and a fixed binary struct would need its own versioning and couldn't reuse the schema.
- A JSON header is validated by the same strict schema and duplicate-key parser as text messages. The 1024-byte cap bounds the parse; a real header is about 150 bytes.

**Receiver checks**, in order, with the §4 handling on failure: total length ≥ 6, known `frame_type`, `header_len` within range and within the message, header parses as strict UTF-8 JSON and validates, JPEG present and starts `FF D8`. The relay then applies the frame fence (ARCHITECTURE §4: current live kiosk attachment and grant, rechecked at the writer) and forwards the binary message unchanged to the owning staff socket, or drops it. Under pressure the relay drops frames, never commands. The desktop runs the §2.3 display boundary; `frame_displayed` echoes the four binding IDs from the header.

## 8. Terminal reasons (closed registry)

`support_stopped` and `attachment_ended` carry exactly one of these. The tablet may send only tablet-origin reasons (`$defs/tablet_terminal_reason`); `attachment_expired` from the tablet is always `lease_expired`. The desktop shows the fixed string, never page content.

| Reason | Origin | Desktop shows |
|---|---|---|
| `local_stop` | tablet | Support stopped locally |
| `grant_expired` | tablet or relay | Support approval expired |
| `lease_expired` | tablet or relay | Attachment expired |
| `focus_lost` | tablet | Kiosk lost focus |
| `obscured` | tablet | Kiosk obscured |
| `sensitive_state` | tablet | Kiosk unavailable for sharing (also unknown states and the a11y `secure_window` screenshot error) |
| `geometry_changed` | tablet | Kiosk view changed (also navigation, page load, URL generation) |
| `banner_lost` | tablet | Support banner unavailable |
| `suspend` | tablet | Tablet suspended |
| `screen_off` | tablet | Screen off |
| `service_failure` | tablet | Tablet service unavailable |
| `enrollment_opened` | tablet | Enrollment opened |
| `detached` | relay | Attachment ended |
| `disconnected` | relay | Connection lost |
| `revoked` | relay | Access revoked (also session end and device revocation) |
| `policy_changed` | relay | Support policy changed (also scope, role or policy changes) |

The relay rejects a tablet reason with the wrong origin (schema-invalid, §4). The first serialized terminal transition wins; later ones for the same attachment are ignored.

## 9. Error codes

Every WSS error is `{"v":1,"type":"error","id":<request id|null>,"error":{"code":<code>}}` with no other detail: no secrets, URLs, args or stack traces. "Close" means the sender closes the WebSocket right after sending the error. "Retry" is what an automatic client may do; a person can always start a new, separate action.

| Code | Sent when | Close | Retry |
|---|---|---|---|
| `UNAUTHENTICATED` | Pre-auth violation, bad or revoked token (also `session_ended`) | Yes | No. New login only |
| `FORBIDDEN` | Role or scope denies the op | No | No |
| `SESSION_EXPIRED` | Absolute or idle session expiry (in `session_ended`, or as a reply racing it) | Yes | No. New login only |
| `DISABLED_BY_POLICY` | A gate or policy blocks the op; reserved ops; staff login switched off | No (yes in `session_ended`) | No |
| `DEVICE_AUTH_FAILED` | Any device-auth failure: unknown, pending, revoked, bad proof, stale challenge | Yes | Tablet: only as ARCHITECTURE §3.2 allows during enrollment; otherwise no automatic retry |
| `LEASE_BUSY` | Another owner holds the device's attachment | No | No automatic retry |
| `LEASE_REQUIRED` | No live attachment held by this session and socket for the device | No | No. Attach again |
| `GRANT_REQUIRED` | The op needs a valid grant and there is none | No | No. New kiosk attachment and fresh local approval |
| `ATTACHMENT_STALE` | The `attachment_id` names an attachment that existed on this device but is released or replaced | No | No. Discard local state for that ID |
| `GRANT_STALE` | The `grant_id` is not the attachment's current grant | No | No |
| `FRAME_UNKNOWN` | No ring record matches the four binding IDs | No | No. Re-target on a newer displayed frame with a new `command_id` |
| `FRAME_NOT_DISPLAYED` | The frame is not the latest acknowledged displayed frame | No | as above |
| `FRAME_EXPIRED` | The frame is older than `FRAME_MAX_AGE_MS` at dispatch | No | as above |
| `GENERATION_STALE` | The frame's generation is no longer current | No | as above |
| `GESTURE_OUT_OF_BOUNDS` | A path point lies outside the content rect or inside an exclusion | No | as above |
| `OVERLOADED` | Queue (32/device), rate (20/s/session) or retained-dedup set is full | No | Yes, once, after ≥ 1 s, with the same `command_id` (it was not recorded). Coordinate ops will usually need a fresh frame instead |
| `DEADLINE_EXCEEDED` | The command deadline passed before dispatch (relay or tablet) | No | No. Never replayed |
| `DUPLICATE_ID_CONFLICT` | Same `(attachment_id, command_id)` with different content | No | No. Client bug |
| `OUTCOME_UNKNOWN` | A send was attempted and no definitive ack exists (`cmd_result` only) | No | **Never.** Check device status; a wipe needs a new step-up |
| `DISCONNECTED` | The target tablet has no authenticated socket | No | No automatic retry; wait for `device_status` |
| `RESERVATION_EXPIRED` | The tablet's wipe reservation is unknown or past its local expiry (ack `err`, mapped to `rejected_expired`) | No | No. A new wipe needs a new step-up |
| `UNSUPPORTED` | `v` ≠ 1, unknown message type, unknown frame type byte; as an ack `err`, an op this tablet cannot perform (wipe below API 34, `kiosk_back` at the history root or with an uncertain history entry, remote touch disabled for the build) | Yes as `error`; no as ack `err` | No |
| `INVALID_MESSAGE` | Malformed or schema-invalid input (§4) | Yes | No |

## 10. HTTP routes

Bodies are defined in `http-v1.schema.json` (`$defs/<name>.request` and `.response`). All JSON bodies reject unknown and duplicate fields. Every response sets `Cache-Control: no-store`; auth responses also set `Referrer-Policy: no-referrer`. "admin" means `Authorization: Bearer <session token>` with live authorization at execution; tokens are never accepted in a query string. A status secret is never accepted as a session token.

| Method and route | Auth | Request (`$defs`) | Success (`$defs`) |
|---|---|---|---|
| `POST /auth/transactions` | none (login gate) | `auth_transactions.request` `{port, state_d, challenge_d}` | `200` `auth_transactions.response` `{start_url}` |
| `GET /auth/start/<start_id>` | none | — | `200` HTML confirmation form; sets `__Host-rc_<start_id>` |
| `POST /auth/continue` | binding cookie, CSRF, exact `Origin` | form (`application/x-www-form-urlencoded`) with fields of `auth_continue.form` `{start_id, csrf}` | `303` to the IdP |
| `GET /auth/callback?code&state` | binding cookie | — | `302` to `http://127.0.0.1:<port>/cb?code=…&state=<state_d>` |
| `POST /auth/token` | none (code + verifier) | `auth_token.request` `{code, verifier_d}` | `200` `auth_token.response` `{token, expires_at}` |
| `POST /auth/step-up/transactions` | staff bearer | `step_up_transactions.request` `{device_id, op:"wipe", port, state_d, challenge_d, confirmed:true}` | `200` `step_up_transactions.response` `{start_url}`; `409` if one is pending |
| `POST /auth/step-up/token` | the original staff bearer | `step_up_token.request` `{code, verifier_d}` | `200` `step_up_token.response` `{step_up_id, expires_at}` |
| `POST /auth/logout` | own session | `logout.request` `{}` | `200` `logout.response` `{state:"logged_out"}` |
| `POST /enroll/requests` | unauthenticated supervised tablet | `enroll_create.request` `{spki_der_b64, security_level}` | `201` `enroll_create.response` `{request_id, device_id, fingerprint, expires_at, status_secret}` |
| `GET /enroll/requests/<id>/status` | `Bearer <status_secret>` | — | `200` `enroll_status.response` `{state, expires_at}` |
| `POST /enroll/requests/<id>/abandon` | `Bearer <status_secret>` | `enroll_abandon.request` `{}` | `200` `enroll_abandon.response` `{request_id, state}` (idempotent) |
| `GET /enroll/requests?cursor&limit` | admin | — (`limit` 1–100) | `200` `enroll_list.response` `{items, next_cursor}` |
| `PUT /devices/<device_id>/scope` | admin | `device_scope.request` `{group_id}` | `200` `device_scope.response` `{device_id, group_id}` |
| `POST /enroll/requests/<id>/approve` | admin | `enroll_approve.request` `{fingerprint, accept_software}` | `200` `enroll_approve.response` `{request_id, device_id, group_id, state:"approved"}` |
| `POST /enroll/requests/<id>/reject` | admin | `enroll_reject.request` `{}` | `200` `enroll_reject.response` `{request_id, state:"rejected"}` |
| `GET /audit?cursor&limit` | admin | — (`limit` 1–100) | `200` `audit.response` `{items, next_cursor}` |
| `POST /devices/<device_id>/revoke` | admin | `device_revoke.request` `{}` | `200` `device_revoke.response` `{device_id, state:"revoked"}` |
| `POST /sessions/<session_id>/revoke` | admin | `session_revoke.request` `{}` | `200` `session_revoke.response` `{session_id, state:"revoked"}` |
| `POST /enroll/reconcile` | admin | `reconcile.request` `{fingerprint, request_id?}` | `200` `reconcile.response` `{fingerprint, request_id?, outcome:"cleared"}` |

- The enrollment status route returns the same generic `401` for an unknown ID and for a wrong or missing secret.
- Audit items are `contracts.AuditEvent` plus the store-assigned `event_id` and `occurred_at`; `principal` is `{issuer, subject}` or `null`.
- Errors use the body `error_body` `{"error":{"code"}}`:

| Code | Status | Retry |
|---|---|---|
| `INVALID_REQUEST` | 400 | No |
| `UNAUTHENTICATED` | 401 | No. New login (or, for a tablet, stop) |
| `FORBIDDEN` | 403 | No |
| `NOT_FOUND` | 404 | No. Also returned for out-of-scope targets |
| `CONFLICT` | 409 | No automatic retry; reload state first |
| `EXPIRED` | 410 | No. Start a new transaction or request |
| `RATE_LIMITED` | 429 | Yes, with bounded backoff (tablet status polling only); interactive callers surface it |
| `UNAVAILABLE` | 503 | Yes, with bounded backoff, for idempotent reads and `abandon` only |

## 11. Message catalog

The schema `$defs/<direction>` lists the complete set; each message is `$defs/<s2r|r2s|r2d|d2r>.<type>`.

- **Staff → relay:** `staff_auth`, `list_devices{cursor?}`, `attach`, `detach`, `lease_renew`, `frame_displayed`, `cmd`, `logout`.
- **Relay → staff:** `staff_ready`, `devices{items:[{device_id, state:"online"|"offline", caps|null}], next_cursor}`, `attach_result`, `detach_result`, `lease_renew_result`, `support_pending`, `support_granted`, `support_stopped`, `attachment_ended`, `device_status`, `device_disconnected`, `cmd_result`, `error`, `session_ended{code}`, `logout_result{state:"logged_out"}`, binary frame.
- **Relay → tablet:** `device_challenge`, `device_ready`, `attach_open`, `lease_renewed`, `detach`, `frame_displayed`, `cmd`, `reserve`, `execute`, `error`.
- **Tablet → relay:** `device_auth_start`, `device_auth_proof`, `hello`, `status`, `support_pending`, `support_granted`, `support_stopped`, `attachment_expired`, `reserved`, `ack`, `error`, binary frame.

`status` and `device_status` carry `{lock_task_state, owner_verified, destination_id, battery, wifi:{connected, rssi_dbm}, caps:{a11y, window_capture, remote_touch}}` and never a URL: `destination_id` is a compiled identifier such as `equity_home` (`^[a-z0-9_]{1,64}$`) or `null`.
