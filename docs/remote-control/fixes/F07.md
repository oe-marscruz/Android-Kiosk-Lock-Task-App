# Finding 7: projection consent and startup

Replaces/amends: §2.2 (the `RemoteAgentService` and `ScreenCaptureService` bullets), §5.1–5.2, §5.4–5.5. Other §2.2 bullets and §5 items remain for their respective reviews.

## Drop-in replacement

### §2.2 — replace the two service bullets
- `remote/RemoteAgentService`: separate `specialUse` foreground service for the outbound WSS connection and reconnect. It does not acquire MediaProjection or run with the `mediaProjection` type.
- `remote/ScreenCaptureService`: separate `mediaProjection` foreground service, started only after local Android consent; it owns one MediaProjection, VirtualDisplay, ImageReader and JPEG stream per session. Projection is gated by the kiosk capture boundary and local support opt-in; consent alone does not authorize capture of other apps or the whole display. If that boundary cannot be enforced, projection stays disabled.

### §5 — replace items 1–2 and 4–5
1. **MediaProjection consent:** Android 14 introduced single-app sharing. Android 15 QPR1+ adds a prominent status-bar chip and automatically stops projection when the screen locks; do not assume this behavior on earlier Android 15 builds. Each session needs fresh system consent, tapped by a person at the tablet. Neither Device Owner nor accessibility automation accepts or bypasses the dialog. A remote request is only a request; it cannot grant consent or trigger background UI contrary to Android activity-start restrictions. Use a visible, locally initiated activity to request consent. Denial, cancellation, timeout, inability to show the activity/dialog, or loss of the authorized attachment ends the attempt without frames. [Android media projection](https://developer.android.com/media/grow/media-projection).
2. **Lock task and system dialogs:** Test the exact deployed `setLockTaskFeatures` flags, allowlisted activities, immersive-sticky UI, and banner/overlay behavior on the K11. Record the baseline and separately test `LOCK_TASK_FEATURE_SYSTEM_INFO` (status-bar system indicators) and `LOCK_TASK_FEATURE_BLOCK_ACTIVITY_START_IN_TASK`; neither is assumed to make the consent dialog work. Verify the dialog is visible and clickable, and that the system indicator and stop affordance are accessible where supported. Do not loosen the kiosk boundary to make projection work. A per-build `PROJECTION_ENABLED` switch defaults false; enable only for a device/OS and app build that passes this checkpoint. If the dialog or required indicator/stop interaction fails, disable projection for that build and report it unavailable. [Lock task features](https://developer.android.com/work/dpc/dedicated-devices/lock-task-mode).
4. **FGS types and session order:** Declare `android.permission.FOREGROUND_SERVICE`, `android.permission.FOREGROUND_SERVICE_SPECIAL_USE`, and `android.permission.FOREGROUND_SERVICE_MEDIA_PROJECTION`. Declare `RemoteAgentService` as `specialUse` with `android.app.PROPERTY_SPECIAL_USE_FGS_SUBTYPE` justification; declare `ScreenCaptureService` as `mediaProjection`. Use each service's corresponding type in `startForeground()`. From the visible local activity: request `createScreenCaptureIntent()` → local user approves → start the separate projection service and promote it to `mediaProjection` foreground → call `getMediaProjection()` using that result → register `MediaProjection.Callback` → create one VirtualDisplay and begin frames. A consent result is used once and a projection instance creates only one VirtualDisplay; a new session requires a new request and consent. Never persist or replay the result. Handle failed service start, invalid result, and exceptions as a stopped session. [FGS types](https://developer.android.com/develop/background-work/services/fgs/service-types), [media projection](https://developer.android.com/media/grow/media-projection).
5. **Stop and boot:** On callback `onStop`, local stop, detach, disconnect, focus/boundary loss, or failure, stop frame delivery, release VirtualDisplay, ImageReader and surfaces, stop projection and its FGS, clear the consent result, and report stopped; cleanup is idempotent. No automatic restart or reuse after process death. Boot may start only the `specialUse` agent, subject to platform restrictions and device verification; it never starts projection or obtains consent. Android 15 restricts starting `mediaProjection` FGS from `BOOT_COMPLETED` for apps targeting API 35+. [Android 15 FGS restrictions](https://developer.android.com/about/versions/15/behavior-changes-15#fgs-boot-completed).

## Acceptance tests
- Unit: drive approval, denial, cancel, timeout, detach and failure through the state machine; assert no projection service or frames before approval, exact startup order, one use of result and VirtualDisplay, idempotent cleanup, and no automatic restart. Disabled `PROJECTION_ENABLED` rejects projection requests and reports unavailable.
- Emulator API 35: inspect merged manifest for all three permissions, distinct service types and special-use property; boot and confirm only the agent starts. With an authorized visible activity, approve and cancel separate requests; verify startup, callback cleanup, no result reuse and no frames after stop. Repeat with background activity launch blocked.
- K11 checkpoint: record OS build/QPR, app build, exact DPM lock-task flags and immersive/overlay settings. In actual lock task, test consent approval and cancellation, foreground activity launch, dialog visibility/touchability, and indicator/stop interaction with baseline and the two flag variations. On QPR1+ test chip stop and screen lock, verifying callback and resource cleanup. Verify no other app or screen content is streamed. Enable the switch only after all required checks pass; otherwise leave it false for that build.

## Interfaces touched
- `RemoteAgentService`, `ScreenCaptureService`; local consent activity and `MediaProjection.Callback`.
- Build configuration `PROJECTION_ENABLED` (default false); existing `attach{mode:"projection"}` and device capability/status reporting must expose unavailability and stopped/denied outcomes. Coordinate exact status fields with the protocol owner.
