# H03 — Enrollment through activation

**Replaces/amends:** ARCHITECTURE.md v0.3 §2.2 (enrollment panel), §3.2 (Enrollment, Device auth, States), §3.4 (Groups and enrollment routes), §5.6 (auth failures), and §4 (device handshake fixtures). Other §1 decisions and §3.2 supervised trigger and StrongBox rules remain.

## Drop-in replacement

### §2.2 Enrollment panel

- The supervised USB trigger opens the native `MainActivity` panel. It blocks support and remote input. Its five-minute lifetime starts on opening and is never extended. Request expiry is independently ten minutes from relay creation; the earlier deadline wins locally. Focus loss, process death, Cancel or deadline closes the panel and abandons any unfinished enrollment. A new attempt needs a new supervised trigger.
- Panel states: **Start** → **Generating key** → **Request created** (show request ID and full fingerprint) → **Waiting for admin** → **Finish enrollment** → **Proving key** → **Active**. Start, Cancel and Finish are local actions. Finish is enabled only after authenticated status reports approval, and starts the WSS proof; approval alone never activates. Only `device_ready` completes the panel. Show a bounded error and permit retry inside both original deadlines; never silently create a replacement request. On expiry or rejection, show the outcome and close after cleanup.

### §3.2 Enrollment and authentication

- Start creates a fresh EC P-256 Android Keystore alias unique to this attempt. Submit its SPKI and security level as specified. The relay returns the existing fields plus `status_secret`, a random 256-bit request-scoped bearer secret over HTTPS, once. Keep it in private app memory only, never display, log, or send via WSS. It authorizes only status and abandonment for that request, not activation or administration. Store only a verifier server-side; rate-limit these endpoints. TLS and the unguessable secret protect registry state. A process death abandons the attempt, not restores the secret.
- The tablet polls `GET /enroll/requests/<id>/status` with `Authorization: Bearer <status_secret>` using bounded backoff until approval or termination. Valid responses contain only `state` (`pending`, `approved`, `active`, `rejected`, `expired`, `revoked`, `abandoned`) and the original `expires_at`. Unknown ID, invalid secret and missing secret have the same generic `401 UNAUTHENTICATED` response. A request tombstone retains its verifier and terminal state for a bounded cleanup window after expiry so the holder can learn the outcome; thereafter all status calls return the same generic 401. Never put the secret in a URL. These endpoints are no-store and follow §2.1 logging rules.
- After Finish, the existing challenge and signature exchange applies. The relay atomically consumes the challenge and changes `approved → active` only if proof is valid and the original request TTL has not elapsed. A lost `device_ready` can be recovered by authenticated status reporting `active`, followed by a fresh WSS proof; the panel completes only on `device_ready`. Retries use fresh challenges and remain within both deadlines. No `hello`, support or input precedes `device_ready`.
- All WSS authentication failures remain the same `DEVICE_AUTH_FAILED` and close, including unknown, pending and revoked identities. While a live enrollment attempt exists, the tablet checks its authenticated status: `pending` waits, `approved` offers Finish/retry, `active` retries proof, and terminal states stop and clean up. A generic status failure or network outage is not evidence of revocation: retry only within the deadlines, then clean up. Outside enrollment any WSS auth failure stops automatic retries and requires supervised diagnosis. This does not reveal registry state to unauthenticated callers.
- Cancel, focus loss, process death, local or relay expiry, rejection, or key replacement stops proof and support immediately. Persist a non-secret cleanup marker before key generation, with the alias and request ID if known. Send idempotent `POST /enroll/requests/<id>/abandon` using the secret while available; atomically transition pending or approved to abandoned, invalidate challenges and prevent activation. If activation raced cleanup, abandon also revokes that identity and closes its socket under §2.1 ordering. A lost response is retried while the secret remains available; relay TTL expires unfinished requests even if offline. On process restart, delete the marked alias; the server expires unfinished requests. If activation may have succeeded before process death and abandonment cannot be authenticated, the device remains unusable locally and an admin must revoke the orphaned identity before re-enrollment. Never assume a lost response means cleanup succeeded.
- Delete the alias using the loaded `AndroidKeyStore` `KeyStore.deleteEntry(alias)` and verify absence with `containsAlias`. Retry deletion if it fails; block new enrollment and remote use until cleanup succeeds. Erase the secret and local request data after cleanup. Replacement always abandons/revokes the old identity and deletes its alias before generating a new key, request and ID; revoked IDs and keys never reactivate. Android documents [Android Keystore access](https://developer.android.com/privacy-and-security/keystore) and [`deleteEntry`](https://developer.android.com/reference/java/security/KeyStore#deleteEntry(java.lang.String)); deletion may fail and must not be assumed.

### §3.4 Enrollment routes and scope

- Unassigned pending requests are visible to authenticated admins eligible to assign at least one group, with only the listed enrollment fields. Once assigned, they are visible only to admins currently authorized for that group; unknown and out-of-scope requests return 404. Pagination rechecks scope on every page.
- `PUT /devices/<device_id>/scope` assigns an unassigned, unexpired pending request only to a group the admin currently administers. Reassignment of an assigned pending request requires live authority over both groups. Existing active-device reassignment rules remain. Assignment and approval each execute as one transaction with live authorization, state, TTL and scope checks, and required audit; audit failure rolls back. Conditional updates serialize competing operations. Approval requires pending, assigned, unexpired state, current authority over the assigned group, full matching fingerprint and software-key consent when required. A concurrent scope change, rejection, expiry, revocation or approval cannot produce approval under stale authority. Incompatible in-scope state is 409; expiry is 410; unknown or out-of-scope is 404.
- Add `GET /enroll/requests/<id>/status` and `POST /enroll/requests/<id>/abandon` with the request-scoped bearer secret as above; abandon takes `{}` and returns `200 {request_id,state}`. It is idempotent, including when it revokes a raced activation. Admin reject remains separately authorized, state-checked and audited. Never accept the status secret as a staff session.

### §5.6 Retry

- Normal reconnect uses the existing jitter policy. Generic WSS auth failure stops normal reconnect; only the bounded, authenticated enrollment recovery above can retry during an open attempt. A terminal status stops it. No retry extends either deadline.

## Acceptance tests:

- Fixtures cover every panel transition, status and terminal response, secret authentication, generic WSS errors, Finish, proof and `device_ready`; schema rejects unknown fields and secrets never appear in logs or URLs.
- On a K11 and mock relay, perform supervised Start, full physical fingerprint comparison, assignment, approval, local Finish and valid proof; assert no activation before proof and no support before ready. Delay approval, drop status or ready responses, and reconnect; retries stay within both original deadlines and recover only as specified.
- Cancel, expiry, rejection, focus loss, process death and key replacement at each stage, including a proof/abandon race and offline relay. Assert alias removal, terminal relay state or TTL cleanup, orphan escalation where needed, no reactivation and no remote use. Inject delete and audit failures; verify fail-closed behavior.
- Test pending, unknown and revoked WSS starts produce indistinguishable failures; only a valid request secret reveals status. Test invalid/missing secret and unknown ID, rate limits, expiry and replay. Verify active authentication failure outside enrollment stops retries.
- Race assignment, reassignment, approval, rejection, expiry, revocation and scope removal; assert one valid serialized result, no stale-scope approval, no out-of-scope list or lookup, and rollback on audit failure. Test software consent and full fingerprint mismatch.
