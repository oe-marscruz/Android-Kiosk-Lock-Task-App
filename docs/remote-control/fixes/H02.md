## Drop-in replacement Markdown

### §2.1 — Trusted authorization contracts

`StaffSession` is an identity reference, not authority. Contexts are frozen snapshots built by the relay from authenticated connections and authoritative state while holding the ordering lock, never from client-supplied claims. IDs supplied on the wire are lookup keys, not proof of ownership. Deadlines are absolute relay deadlines in a single monotonic clock domain; session validity is also checked against its authoritative expiry and revocation state. Missing, expired, inconsistent or unavailable state denies. Snapshots do not themselves grant authority.

```python
@dataclass(frozen=True)
class WsAttachContext:
    device_id: str
    socket_id: str
    attachment_id: str | None
    grant_id: str | None
    lease_deadline: float | None
    grant_deadline: float | None
    maintenance_active: bool
    policy_revision: int
    requested_mode: Literal["status", "kiosk"]

@dataclass(frozen=True)
class WsCommandContext:
    device_id: str
    socket_id: str
    attachment_id: str
    grant_id: str | None
    lease_deadline: float
    grant_deadline: float | None
    maintenance_active: bool
    policy_revision: int

@dataclass(frozen=True)
class HttpMgmtContext:
    device_id: str | None
    target_session_id: str | None
    from_group: str | None
    to_group: str | None
    policy_revision: int

@dataclass(frozen=True)
class StepUpContext:
    device_id: str
    socket_id: str
    attachment_id: str
    grant_id: str
    lease_deadline: float
    grant_deadline: float
    maintenance_active: bool
    policy_revision: int

class SecurityServices(Protocol):
    async def authorize(self, session_id: str, op: str,
                        ctx: WsAttachContext | WsCommandContext | HttpMgmtContext | StepUpContext) -> Decision: ...
    async def consume_step_up(self, session_id: str, op: str,
                              step_up_id: str, ctx: StepUpContext) -> Decision: ...
```

The operation determines the required variant and required targets; mismatched variants, absent required targets and extraneous targets deny. For reassignment, `device_id`, `from_group` and `to_group` come from the current registry and validated request; check authority over both groups. For session revocation, `target_session_id` identifies the target whose entire current scope is checked. Management operations without an attachment do not fabricate socket or grant fields. Attach from `none` has no attachment, grant or deadlines; a same-owner transition carries the current attachment and lease. Authorization checks the session, socket ownership, current attachment identity and state, mode, deadlines, grant binding, maintenance state, scope, role and feature gate as applicable. The context revision and all relevant snapshot values must still match live state; otherwise rebuild and authorize or deny. Only the current authoritative state decides.

**Revision and ordering.** Maintain a monotonically increasing `policy_revision` for the running relay. Atomically publish a new revision with each successful policy/config reload, session or device revocation and device reassignment, before releasing the affected locks. Failed reloads leave the old policy and revision intact. Startup establishes a fresh revision with empty queues; revisions need not survive restart. Session expiry, logout and attachment/grant transitions also invalidate matching queued work under the same ordering even if no revision changes. Global and session mutations acquire affected device locks in deterministic order; a global revision publication is coordinated with all device writers so no writer can observe a partially published policy. Purge affected queues and close affected sockets/attachments before mutation success; durable revocation remains effective if cleanup fails. Audit failure or unavailable authoritative state fails closed.

**Socket-writer fence.** Every outgoing command, frame and scoped event carries trusted routing metadata: device, intended socket and session, attachment and grant where applicable, operation, and revision at enqueue. The sole writer for each socket reacquires the same per-device ordering immediately before `ws.send`, resolves current state and authorizes the item for its direction and operation. It checks the current revision, session validity and scope, socket and current attachment ownership, grant and lease deadlines, maintenance and device state as applicable. Revision mismatch requires fresh authorization against current state; stale attachment, expired grant or denied authority is dropped. Content-free terminal notifications needed for cleanup may be sent only through a separately defined non-scoped path, without student content or stale authority. Unscoped handshake traffic is outside this fence.

Hold the ordering through the actual bounded send so a mutation cannot commit between the final check and the write. A stalled or failed send closes the socket and fails closed; it cannot hold the lock indefinitely. If a mutation commits after enqueue but before the writer takes the lock, the writer observes the new state and drops or reauthorizes the item; enqueue is not forwarding. If the writer wins, bytes already handed to the transport cannot be recalled. Purge is defense in depth, not a substitute for the writer check. Preserve audit-before-dispatch and never replay an unacknowledged command.

**v1 scope source.** `ROLE_SOURCE=principal` is the only supported v1 source: `ACCESS_MAP` is keyed by `(iss, sub)`. Reject `ROLE_SOURCE=group` at startup and reload. A future group source needs an authoritative live membership source, a bounded freshness contract and ordered invalidation before it can be enabled. No token-cached membership, email fallback or stale mapping grants access.

### §3.3 — HTTP step-up binding

At transaction initiation and redemption, use the authenticated HTTP session and `device_id` to look up that device's current live attachment under its device lock. It must be a kiosk attachment owned by that same session and its still-live WSS socket, with a current valid local grant and lease. Build `StepUpContext` from that attachment; HTTP does not supply or infer a socket from a bearer token. Bind the transaction and resulting step-up to the resolved socket, attachment and grant IDs in addition to the existing principal, session, device, op and confirmation. Re-resolve and compare at redemption and at atomic consumption during command dispatch. Replacement, disconnect, expiry, revocation or any binding mismatch denies and invalidates the pending transaction/grant; a new attachment requires a new confirmation and step-up. The existing freshness and feature-gate checks still apply.

### §§3.4 and 4 — Management and delivery

Build `HttpMgmtContext` from the current registry and the validated target for each management request; check scope at execution, including on each audit page. Device-less and unassigned enrollment operations use their explicit §3.4 rules. Apply the writer fence in both directions to commands, frames and all device- or attachment-scoped events, including queued results and status events. The §4 protocol registry defines which items are scoped and their routing metadata; metadata is internal and is not an additional client credential.
