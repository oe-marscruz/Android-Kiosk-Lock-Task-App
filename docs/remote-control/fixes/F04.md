### Replacement for the `kiosk_remote/auth.py` bullet in §2.3
- `kiosk_remote/auth.py`: login via the system browser, a relay-registered transaction and an exclusive `127.0.0.1` loopback listener (§3.1).

### 3.1 Staff login (desktop ↔ relay ↔ Duo SSO)

The relay is the OIDC confidential client; its callback is the fixed `PUBLIC_BASE_URL/auth/callback`. The desktop handoff is a separate application protocol, not an OIDC redirect registered with Duo. Use the system browser and loopback only while login is pending ([RFC 8252 §§7.3, 8.3](https://www.rfc-editor.org/rfc/rfc8252.html#section-7.3); [RFC 9700](https://www.rfc-editor.org/rfc/rfc9700.html)).

1. Desktop generates independent cryptographically random `state_d` and `verifier_d` (32 random bytes each, base64url without padding); `challenge_d` is base64url-no-padding SHA-256 of the ASCII verifier. Bind and listen on IPv4 `127.0.0.1`, OS-assigned port, before any registration or browser launch. On Windows set `SO_EXCLUSIVEADDRUSE` before bind; do not enable address reuse. Abort on bind failure. Never listen on a wildcard or forward the callback.
2. Desktop sends HTTPS `POST /auth/transactions` with JSON `{port, state_d, challenge_d}`. Validate `port` as an integer in 1–65535, and state/challenge as canonical 43-character base64url encodings of 32 bytes; reject unknown fields and duplicate parameters. The relay stores them with an independent random 256-bit `start_id`, pending for 5 minutes, and returns JSON `{start_url}` with `https://<configured relay>/auth/start/<start_id>`. The desktop opens this URL in the system browser. Never accept a supplied redirect URL or hostname.
3. Browser `GET /auth/start/<start_id>` validates the pending, unexpired transaction but does not authenticate or consume it. Set a per-transaction random 256-bit browser binding in a cookie named `__Host-rc_<start_id>` with `Secure; HttpOnly; SameSite=Lax; Path=/; Max-Age=300`, no Domain. Store its hash against the transaction; do not replace an existing binding on repeated GET. Serve a same-origin confirmation form with a separate random CSRF token bound server-side to that transaction and cookie. Browser `POST /auth/continue` submits `start_id` and `csrf`; require the matching cookie, token, exact relay Origin, unexpired pending transaction and single-use atomic transition to OIDC-in-progress. Reject cross-origin, missing, mismatched, expired or repeated submissions. A consumed start URL cannot start another flow.
4. Relay generates independent OIDC `state`, `nonce` and PKCE verifier; stores them with the transaction and browser binding; redirects to the configured Duo authorization endpoint with `response_type=code`, `client_id`, fixed `redirect_uri`, `scope=openid email profile`, `state`, `nonce`, `code_challenge` and `code_challenge_method=S256`. `GET /auth/callback` requires exactly one matching state and the same browser cookie, an unexpired in-progress transaction, and exactly one code or error. Atomically claim the transaction before exchanging the code; errors, exchange failures or validation failures terminate it and require a fresh login. Exchange the code at the configured token endpoint with client authentication, fixed redirect URI and the relay PKCE verifier. Validate ID token signature and claims including issuer, audience, expiry and the stored nonce; apply the MFA, principal and role policy in §3.3. Never issue a handoff on failure. The cookie is deleted using the same name and attributes on completion or error.
5. After authorization, mint a random 256-bit one-time handoff code, valid 60 seconds, bound to `challenge_d` and the authorized principal. Atomically mark the transaction completed. Redirect to `http://127.0.0.1:<port>/cb?code=<code>&state=<state_d>` constructed only from the literal address, validated decimal port and fixed path; encode query values. The desktop accepts only `GET /cb` with exactly one code and one matching `state_d`; reject malformed, duplicate, wrong-path or wrong-state requests without redeeming or closing the listener. Return a minimal success page without external resources, then close the listener on an accepted callback, cancellation or the 5-minute deadline. Limit request size and read time; do not block the Tk UI.
6. Desktop sends HTTPS `POST /auth/token` JSON `{code, verifier_d}`. In one atomic operation verify the code is unexpired and unused and that S256 of the verifier matches its bound challenge, consume it and create the session; concurrent redemption can produce at most one session. Reject invalid verifier without consuming the valid code. Return an opaque 256-bit session token, 8-hour absolute TTL and 30-minute idle timeout, revocable and stored server-side as a hash. Desktop keeps it in memory only; Duo/OIDC tokens never leave the relay.

All auth responses, including loopback responses, use `Cache-Control: no-store` and `Referrer-Policy: no-referrer`; pages have no third-party resources. Redact auth paths' query strings, start IDs, cookies, codes, state, CSRF tokens, verifiers and tokens from application and Caddy access/error logs; never log request bodies or authorization headers. Use HTTPS and certificate/hostname validation for relay traffic. Rate-limit registration, continuation and redemption; expire and remove abandoned transaction state. A user-owned Duo trial with a local relay is tested first; CU uses the same flow with configuration changed.

### Acceptance tests:
- With a mock OIDC provider and real HTTP clients, complete registration → confirmation → OIDC callback → loopback → redemption; assert identity, one session, cookie flags, exact fixed redirect and response headers. Run the local-relay flow with the user-owned Duo trial before CU configuration testing.
- Reject altered, missing, duplicated or expired state, nonce, cookie and CSRF; reject cross-origin continuation, callback before continuation, callback replay, failed token exchange and unauthorized principal. Parallel continuation and callback requests each advance at most once. Test separate concurrent browser transactions without cookie collision.
- Reject port 0, 65536, string, negative and malformed challenge; prove registered port cannot inject host, path or query. Reject expired/used handoff, wrong verifier and concurrent double redemption; assert exactly one session and retry with the correct verifier after a wrong one.
- On Windows 10 and 11 as standard user, occupy the listener port and verify exclusive bind fails; exercise wrong path/state, duplicate parameters, oversized and stalled requests, cancellation and timeout. Verify only loopback is reachable and successful login needs no firewall exception.
- Inspect relay, proxy and desktop logs and browser responses across success and failure: no secret, query string or request body appears, no cached auth response or external page resource exists. Verify a fresh start after timeout or failure.
