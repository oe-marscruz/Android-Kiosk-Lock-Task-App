# H01 — Tablet attachment lifecycle

**Replaces/amends:** ARCHITECTURE.md v0.3 §§2.2 (invalidation), 3.3 (policy table, attachment lifecycle), 4 (relay → device and admission).

## §3.3 Policy table

Replace the `attach` row with:

| Op | Min role | Attachment | Grant | Policy | Decision / conditions |
|---|---|---|---|---|---|
| `attach{status}` / `attach{kiosk}` | viewer | — | N | * | Allowed in scope, subject to lease rules. Kiosk requests approval. |
| `attach{status}` / `attach{kiosk}` | viewer | status | N | * | Current owning session and socket only. Same mode returns current state without extending deadlines; kiosk replaces the attachment and requests approval. |
| `attach{status}` / `attach{kiosk}` | viewer | kiosk | * | * | Current owning session and socket only. Same mode returns current state without extending deadlines; status replaces the attachment and revokes the grant. |

A different owner gets `LEASE_BUSY`. All transitions remain subject to live authorization and scope.

## §§3.3, 4 Lifecycle and wire messages

Replace the relay → device `support_request` entry with `attach_open{attachment_id, mode, display_name?, lease_ms}`, `lease_renewed{attachment_id, lease_ms}`, and `detach{attachment_id}`. These are unsolicited events. `mode` is `status` or `kiosk`; `display_name` is required for kiosk and omitted for status. A kiosk open starts the existing local approval flow; a status open creates a status lease without a prompt or grant. The tablet knows status attachments through this open message.

- On acquisition the relay commits the attachment and sends `attach_open` before any scoped command. Mode replacement releases the old ID, sends `detach(old)`, then opens the new ID. Each open starts a fresh tablet lease; it never transfers consent or state.
- On an accepted renewal, or an authorized substantive op that resets the relay lease, send `lease_renewed` for the current ID before forwarding work relying on that extension. No message extends consent or the approval deadline. Same-mode attach does not renew.
- `lease_ms` is a positive bounded duration no greater than `LEASE_IDLE_S`, calculated from the relay's remaining lease at send time. On receipt the tablet sets its local expiry to its own monotonic `elapsedRealtime()` plus that duration. Relay and tablet deadlines are independent; relay admission still checks its own deadline. No absolute relay timestamp is used by the tablet.
- A renewal applies only to the current, unexpired ID on the current device connection. An expired or released ID cannot be revived. Open, renew and detach are ordered on that connection; stale messages never affect a replacement ID. Disconnect clears all attachment state.
- The tablet checks lease expiry before each scoped operation and schedules local expiry independently of relay messages. At expiry it releases the ID, dismisses any prompt, revokes the grant, stops capture and input and discards scoped queues and frame state. A withheld renewal expires locally even if `detach` never arrives. A late detach for an expired ID is harmless.
- The local approval timeout and grant deadline are separate monotonic deadlines. Approval and use require both the lease and the applicable consent deadline to be live; lease renewal never changes either consent deadline. Local Stop and all §2.2 invalidations remain effective independently of the lease.

## §4 Command deadline

`deadline_ms` on relay → device `cmd` is a positive relative time-to-live, bounded by `CMD_DEADLINE_S`. The relay starts the command deadline at admission on its monotonic clock, rejects expired queued work, and sends only the remaining duration at the socket write. The tablet starts a separate deadline at receipt using `elapsedRealtime()` and rejects the command at or after that deadline, including immediately before dispatch. It also independently checks the current attachment, lease, grant and policy-dependent tablet state.

The relay-to-tablet transit budget is at most 1 second after the socket write; this is a deployment assumption, not a bound the tablet can verify from a one-way message without synchronized clocks. Where the bound holds, the tablet's receipt-relative deadline can exceed the relay admission deadline by at most 1 second. The relay still enforces its own deadline at write; it cannot recall work already written. Commands already dispatched remain subject to the existing outcome rules.

## Acceptance tests:

- Open kiosk, approve locally, then withhold renewal and detach while keeping the connection open. Advance the tablet monotonic clock past its lease: prompt/grant, capture, input and queues are invalidated. A late renewal cannot revive the ID; fresh approval on a new attachment is required.
- Open status, expire it locally, open a new ID, then deliver delayed `detach` for the old ID. The new lease remains live; commands for the old ID fail. Repeat with kiosk and verify no old grant carries over.
- Open status and send `enter_kiosk`: it is accepted only for an active maintenance window and an authorized admin; otherwise denied. No grant or capture is created. After lease expiry it is denied even if detach is delayed.
- Exercise same-owner same-mode and cross-mode attaches in both directions, plus another owner. Check unchanged deadlines for same-mode, new IDs and ordered detach/open for cross-mode, and `LEASE_BUSY` for the other owner.
- Delay a queued command until its relay deadline and reject it; deliver another within the transit budget and advance the tablet clock past its receipt-relative TTL before dispatch: reject it. Advancing or changing wall clocks does not extend either deadline.
