# G09: Publication gate

Replaces/amends: ARCHITECTURE.md v0.2 §7 (P1 and P6 rows and phase ordering), §7.1, §7.2, §8.2; reconciles §2.3 packaging with the interim exception below.

## Drop-in replacement Markdown

### §7: P1 and publication ordering
- P1 owns classification, package inspection and the publication gates in both workflows and packaging scripts. Merge and exercise these gates before **any P3 or P4 remote code merges**. P6 owns the Win10/11 manual release evidence. The P0 review gate still applies.

### §7.1: Artifact classification and verification
- Every candidate has three independent fields: capability (`usb-only` or `remote-capable`), APK (`release` or `debug`), and, on Windows, executable (`authenticode-signed` or `unsigned`). An invalid or unknown field blocks publication. `REMOTE_FEATURES` is an explicit, checked build input, exactly `0` or `1`; missing or other values fail. `1` is remote-capable. `0` is USB-only only if a maintained inventory confirms no remote Android entry points or implementation and no `relay/` or `kiosk_remote/` implementation exists in the source being packaged. Presence of either module or remote Android code makes the candidate remote-capable even if disabled or not bundled; a flag/inventory mismatch fails closed. An unrecognized layout fails closed. CI checks the checkout and package contents, not just a caller-supplied label; update the inventory in the same change as new remote code.
- P1's `build/apk-info.txt` records variant, APK SHA-256 and signer certificate SHA-256. Independently run `apksigner verify --verbose --print-certs` and hash the APK; require exactly the expected signer and compare both values with the record. `release` additionally requires the approved release certificate fingerprint, verified against a protected approved value, and the three `KIOSK_KEYSTORE_B64`, `KIOSK_KEYSTORE_PASS`, `KIOSK_KEYSTORE_ALIAS` secrets. Missing, invalid or mismatched material fails closed. A debug variant is debug even if its certificate happens to match an approved value; never relabel it release.
- Inspect the **final** Windows one-file executable after signing, using a pinned PyInstaller archive extractor, without executing it. Extract the embedded APK and require exactly one expected APK; verify its digest, signature and signer against `apk-info.txt` and the approved fingerprint for release. Verify the final exe's Authenticode signature and RFC 3161 timestamp with `signtool verify /pa /all`; signing errors or invalid signatures fail, never downgrade to unsigned. For macOS, mount the final DMG read-only, inspect the APK in `Kiosk-APK` and every APK embedded in the app bundle or its PyInstaller archive; require the expected copies and matching digest and signer for each. Reject missing, extra, stale or unverifiable copies. Unmount on all paths. Inspect actual published bytes after packaging, not the staging APK alone.
- Record commit, class, APK variant, digest, signer fingerprint, package digest and verification result in release notes or the CI artifact. Never publish secrets. Signing does not establish that an installed fleet APK can be upgraded: inventory and the §7.1 K11 upgrade gate remain required.

### §7.2: Publication matrix
- **Windows default-branch push → rolling `latest`:** only USB-only + debug APK + unsigned exe may publish as an explicitly marked **prerelease**, named `USB-only debug — internal testing — unsigned`, with asset `kiosk-manager-usb-debug-unsigned.exe`. This is the temporary exception in §8.2. USB-only + release APK + signed exe may publish a labelled USB-only prerelease. Remote-capable builds never update `latest`; all other combinations publish nothing. Preserve existing `latest` if a gate fails; never delete or replace it before verification succeeds.
- **Windows `v*` tag:** only release APK + verified signed exe can publish a release. USB-only must be labelled `USB-only`; remote-capable must be labelled `remote-capable` and also pass P0, P5b, §5.7, fleet upgrade and §7.2 Win10/11 manual gates with evidence tied to the candidate commit and package digest. All debug or unsigned tag candidates publish nothing. Asset names include capability, APK variant and signing status. No prerelease or release is silently promoted by a tag.
- **macOS:** the current workflow publishes no GitHub release. It may upload a clearly named internal CI artifact only for USB-only debug builds (`macos-usb-debug-internal`) or USB-only release builds (`macos-usb-release-internal`), after package verification. Remote-capable DMGs are internal CI artifacts only, labelled `macos-remote-release-internal`, and require a verified release APK; debug remote candidates publish nothing. No public DMG prerelease or release is authorized by this design. Internal artifacts are not fleet releases; restrict access using repository and Actions permissions.
- Public release/prerelease publication needs `GITHUB_TOKEN` with `contents: write`; release APKs require the three kiosk secrets above. Signed Windows candidates require CU's approved `WINDOWS_SIGNING_*` mechanism (PFX: `WINDOWS_SIGNING_CERTIFICATE`, `WINDOWS_SIGNING_PASSWORD`, plus `WINDOWS_TIMESTAMP_URL` configuration), successful timestamp and signature verification. The USB debug exception needs no signing secrets. Secrets are never tested directly in `if:`; expose them as job environment variables and test presence in step conditions, or perform the check in a step without logging values. A missing secret resolves to an empty string. See [GitHub secrets documentation](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/use-secrets) and [workflow permissions](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax).
- Untrusted PR jobs may build debug artifacts for CI but cannot publish releases or access release signing secrets. Both branch and tag publication paths independently enforce the complete matrix; a failed check prevents upload as well as release creation or mutation.

### §8.2: Interim fleet signing decision
Keep the rolling USB-only debug/unsigned Windows prerelease temporarily for internal testing while the fleet is inventoried, with the asset name and release title above and a prominent warning: **debug APK, unsigned executable, not a fleet release; each CI run may use a different signing key, so updates to existing installations can fail. Do not uninstall or reset to force an update; inventory the installed signer and follow supervised recovery.** Never instruct staff to bypass SmartScreen. This preserves a test download, not an upgrade channel. Retire the exception once the approved stable signer and signed distribution are available. Fleet key recovery and custody remain open stakeholder work.

## Acceptance tests:
- Exercise every capability × APK variant × Windows signature combination on default-branch and `v*` events, including both module-present/flag-off and remote Android code/flag-off; only matrix-allowed candidates publish, and failures leave `latest` untouched. Confirm P3/P4 changes cannot merge before the gate exists.
- Remove each signing secret, use a malformed keystore, wrong approved signer, invalid timestamp or invalid exe signature; release paths fail without fallback. Verify debug/unsigned interim labels and warnings in the actual prerelease and asset name.
- Change the embedded APK after recording its hash, substitute another valid signer, omit it, add an extra copy, and use stale package contents in both exe and DMG: each blocks publication. Verify a valid final package's extracted APK and signer match its record; inspect all DMG copies. Verify an unsigned remote exe and any remote debug DMG never reach public publication.
- Check `v*` remote publication fails without candidate-bound P0, P5b, §5.7, fleet and Win10/11 evidence; demonstrate successful eligible paths with test credentials and isolated releases. Confirm untrusted PR jobs have no release secrets or write permission.
