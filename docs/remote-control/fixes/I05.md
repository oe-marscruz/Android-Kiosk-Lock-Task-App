# I05 — Crash-safe enrollment completion

**Replaces/amends:** ARCHITECTURE.md v0.4 §2.2 (enrollment panel), §3.2 (Enrollment panel states, Request, Activation, Cleanup, Device auth), §3.4 (enrollment administration), §5.6 (retry), and §4 (enrollment fixtures). The §3.2 `DUMP` gate and local **Start** step remain required.

## Drop-in Markdown

### Tablet durable enrollment state (§2.2, §3.2)

- Store either an unfinished marker `{attempt_id, alias, request_id?}` or an active credential `{device_id, alias}` in one app-private SharedPreferences file. Serialize all reads and writes through one process-local owner; no other process or editor writes it. Attempt IDs and aliases are fresh and unique. Neither the status secret nor private key is stored there.
- After local **Start**, synchronously `commit()` the marker with `attempt_id` and alias, before generating the Keystore key or making a request. After a successful `POST /enroll/requests`, synchronously commit the returned `request_id` into that marker before proceeding. Treat a lost response as a possibly created request. The secret remains memory-only.
- On matching `device_ready`, use one Editor `commit()` to write `{device_id, alias}` and remove every marker field together. Only after `commit()` returns true may the panel show **Active**, send `hello`, or enable remote use. Never use `apply()` for these transitions. Run disk writes off the UI thread and serialize transitions. A failed or uncertain commit fails closed: do not show Active or use the credential; close the socket and restart recovery from durable state, not cached preferences.
- Android documents that [`commit()` atomically applies an Editor's modifications and reports whether persistent storage succeeded](https://developer.android.com/reference/android/content/SharedPreferences.Editor#commit()). As an alternative implementation only, [`AtomicFile`](https://developer.android.com/reference/android/util/AtomicFile) writes and syncs a new file before replacement; it provides no locking, so the same single-owner rule applies. Do not mix primitives for this record.

### Restart and cleanup (§3.2, §3.4, §5.6)

Process death closes the panel and loses the status secret. Never resume a marked attempt or infer relay state from a generic WSS authentication result. On restart, block remote use and new enrollment while resolving the marker; delete the marked alias and verify `containsAlias` is false. Keep the marker and retry if deletion or durable cleanup fails.

- **Before key generation:** marker exists; verify alias absent, then retire marker. A new supervised trigger and Start are required.
- **After key generation, before request dispatch:** delete and verify the alias, then retire marker.
- **After request dispatch, including a lost response or a crash before storing `request_id`:** the request may exist and the secret is lost. Delete the alias; pending/approved requests expire under the original relay TTL. Because activation cannot be ruled out from the marker alone, retain a durable quarantine and require an authorized admin to locate the request by ID if known, otherwise by the attempt's public-key fingerprint or supervised inventory, and confirm it is absent or terminal and any active identity is revoked before clearing quarantine. Preserve or derive the fingerprint before deleting the key when available; inability to identify it requires administrative reconciliation, never automatic clearance.
- **After proof, before active credential commit:** the relay may already be active. Apply the same quarantine and admin revocation rule, even if `device_ready` was received. Authenticated status recovery is unavailable after process death because the secret is gone; treating this as an orphan avoids falsely trusting an unauthenticated status or leaving an active identity usable. Admin revocation uses existing authorized, audited relay ordering; an offline or uncertain result keeps quarantine.
- **After successful active credential commit:** the durable record has the credential and no marker. Restore normal device authentication with that alias; do not delete it as an abandoned attempt. The panel is closed on restart; authentication failure follows existing supervised diagnosis rules.

A crash during a commit must recover as either the complete old record or complete new record, never a mixture. If a marker alone cannot prove that request dispatch did not occur, use the conservative post-dispatch path. Only remove the marker after verified key deletion and, where required, confirmed relay reconciliation, using a successful durable commit. The existing in-process authenticated abandon and bounded status recovery remain available while the secret and panel survive.

## Acceptance tests:

- Inject process death before key generation, after key generation, before request dispatch, after relay request creation with response lost, after response but before request ID commit, and after request ID commit. Verify the appropriate cleanup or quarantine, no remote use, and a new trigger plus Start before retry.
- Kill after proof activates the relay, before `device_ready`, and immediately before, during, and after the credential commit. On restart observe only marker or complete active credential; marker means key deletion and admin reconciliation, active means normal authentication. No Active UI or `hello` precedes successful commit.
- Inject failed commits, key deletion failures, unavailable relay, unknown request ID, and failed or uncertain admin revocation. Assert persistent quarantine, no silent re-enrollment, and eventual clearance only after verified deletion and authorized reconciliation. Verify no status secret survives process death.
- Exercise lost `device_ready` with a still-live panel: authenticated status plus fresh proof recovers within both original deadlines. Confirm the DUMP checks and physical Start remain mandatory.

## Interfaces touched:

- **I02 writer commit:** enrollment credential commit gates `hello` and remote use; relay writer ordering and revocation fencing remain authoritative.
- **I03 terminal messages:** terminal delivery or loss cannot substitute for durable credential commit or authenticated/admin reconciliation.
- **I04 frame fence:** enrollment and quarantine keep support and capture blocked; no frame becomes eligible before committed activation and existing fences.
- **I06 publication:** include these crash and failure fixtures in the enrollment evidence and applicable publication gates.
