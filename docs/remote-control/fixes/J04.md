# J04 — Recoverable enrollment quarantine

## Drop-in Markdown

### Durable enrollment and cleanup (§3.2)

One app-private SharedPreferences file holds either a marker `{attempt_id, alias, request_may_exist: bool, fingerprint?, request_id?, quarantined: bool}` or an active credential `{device_id, alias}`. IDs and aliases are fresh and unique. Fingerprint is SHA-256 of DER SPKI in the existing full display format. The secret and private key are never stored in this record. One process-local owner serializes reads and writes; each transition uses synchronous `Editor.commit()` off the UI thread, never `apply()`. A failed or uncertain commit closes the socket and recovers from durable state; no subsequent step relies on cached state.

After local Start, commit in this order:

1. Marker with `request_may_exist=false`, `quarantined=false`, before key generation.
2. Generate the key, compute its SPKI fingerprint, and commit the fingerprint.
3. Commit `request_may_exist=true` **before** attempting `POST /enroll/requests`. Never revert it.
4. After a successful response, commit `request_id` before proceeding. A lost response may have created a request.
5. On matching `device_ready`, atomically commit `{device_id, alias}` and remove every marker field. Only after success show Active, send `hello`, or allow remote use.

Process death closes the panel and loses the secret. Block remote use and new enrollment while a marker exists. Decide only from the durable record:

| Durable state | Recovery |
|---|---|
| Marker, `request_may_exist=false` | Dispatch was ruled out. If the alias exists and fingerprint is absent, derive and commit it before deletion. Delete the alias, verify `containsAlias` is false, then commit marker removal. If fingerprint preservation or deletion fails, retain the marker and retry. |
| Marker, `request_may_exist=true` | Dispatch may have occurred, including after proof. Commit `quarantined=true`; preserve the fingerprint before deleting the alias. Verify deletion. Retain the marker until authorized reconciliation completes. |
| Missing, invalid, or inconsistent marker fields; dispatch cannot be ruled out | Fail closed and quarantine; preserve or recover the fingerprint before deletion. If identification is impossible, retain the marker for administrative investigation; never automatically clear it. |
| Complete active credential, no marker | Restore normal device authentication; do not delete the alias. |

A crash during a commit yields the complete old or new record. On cancel, focus loss, expiry, rejection or key replacement, the same rules apply. While the panel and secret survive, authenticated idempotent abandon and bounded status recovery remain available; an uncertain result follows quarantine. A marker with `quarantined=true` survives deletion and restart until both verified deletion and required admin reconciliation. Never delete an existing alias before its fingerprint is durably preserved. Never clear quarantine on an unauthenticated status or generic WSS failure.

### Supervised reconciliation (§3.2, §3.4)

A new supervised USB quarantine trigger uses the same DUMP, action, no-extras, Device Owner, sender and focused activity checks as enrollment. It opens a quarantine panel displaying the full durable fingerprint and optional request ID; it cannot start enrollment. An admin at the tablet compares these values with the desktop app, runs reconciliation, observes its successful result, and physically confirms **Clear quarantine** on the tablet. This supervised confirmation conveys the outcome; there is no status secret or unauthenticated relay clearance. The tablet rechecks the same marker and verified alias absence, then commits marker removal. Failure, changed marker, lack of fingerprint, offline or uncertain outcome leaves quarantine intact. A new trigger and Start are required for enrollment.

`POST /enroll/reconcile` takes an admin Bearer session and `{fingerprint, request_id?}` and returns `200 {fingerprint, request_id?, outcome:"cleared"}` only after an authoritative search by fingerprint and, if supplied, matching request ID. Mismatched identifiers, incomplete inventory, ambiguity, or insufficient authority cannot yield clearance. Absence requires authority to search the complete relevant enrollment and device inventory; out-of-scope is not absence. For every matching request or device, require live authority over its scope (and the existing authority for unassigned requests); confirm absent or terminal, or revoke every nonterminal match using existing revocation fencing, invalidating challenges and closing active sockets. Serialize search and revocation against enrollment/activation so no matching identity can become active after clearance; retain sufficient fingerprint tombstones to make absence authoritative. Audit the action, identifiers and outcome; audit failure rolls back mutations and returns no clearance. The operation is idempotent and follows §3.4 error, scope, no-store and denial-audit conventions. The desktop shows success only for the matching response; the tablet does not accept the response directly as authorization.

## Acceptance tests:

- Kill before key generation, after generation, before dispatch, after relay creation with response lost, after response before ID commit, and after ID commit. Verify the durable-field decision, fingerprint preservation before deletion, verified deletion, blocking, and a new trigger plus Start before retry.
- Kill after proof activates the relay, before `device_ready`, and immediately before, during and after credential commit. Recover only a complete marker or credential; marker quarantines, credential authenticates. No Active or `hello` before successful commit.
- Inject failed or uncertain commits, fingerprint preservation failure, deletion failure, unavailable relay, unknown ID, ambiguous or out-of-scope matches, and failed or uncertain revocation/audit. Quarantine persists; no silent re-enrollment or secret survives death. Exercise crashes throughout reconciliation and marker removal.
- Verify reconciliation by ID and fingerprint, authoritative absence, terminal matches and active revocation, including concurrent activation; only a matching successful audited result and supervised confirmation clear the same marker after verified deletion. Test trigger gates and changed-marker rejection.
- With a live panel, recover lost `device_ready` using authenticated status and fresh proof within both original deadlines; retain DUMP checks and physical Start.
