# G06 — Maintenance recovery

Replaces/amends: ARCHITECTURE.md v0.2 §§2.1 (config), 2.2 (tablet agent), 3.3 (exit policy), 4 (maintenance), 5.5 (boot), 7 (P3k), 7.1 (upgrade acceptance).

## Drop-in text

### §§2.1, 3.3 — exit gate

- `EXIT_KIOSK_ENABLED=false` by default, independent of the wipe gate `DESTRUCTIVE_ACTIONS_ENABLED`. Exit requires both its own gate and the existing authorization, consent, confirmation and step-up requirements. It remains off until P3k records passing K11 recovery evidence for the deployed build and policy. Disable it again when those inputs change until reverified. Wipe retains its own gate.

### §§2.2, 4 — ownership and maintenance

- `MainActivity` is the sole owner: its foreground root task explicitly calls `startLockTask()` and only that activity calls `stopLockTask()`. Route an authorized exit through an internal, non-exported command path to the resumed owner in that root task; never stop from the service, launcher or a different task. If that owner cannot be reached and verified, fail the command without claiming exit. Android's API requires an activity that successfully started lock task; AOSP enforces task and caller identity and stopping the root task ends the locked task chain. Verify this on K11. [Activity API](https://developer.android.com/reference/android/app/Activity#stopLockTask()), [AOSP Android 15](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/android15-release/services/core/java/com/android/server/wm/LockTaskController.java).
- Remove `mInLockTask`. On resume and after each transition read `ActivityManager.getLockTaskModeState()`: only `LOCK_TASK_MODE_LOCKED` is success; `NONE` and `PINNED` are not. Confirm Device Owner and `isLockTaskPermitted()` before starting; never fall back to screen pinning. Do not start while keyguard is locked. Check state after the call; exceptions or non-locked state are recovery failures, not success.
- Replace the current `if_whitelisted` on MainActivity, LauncherActivity and WifiSettingsActivity with `normal`, so launching HOME or Wi-Fi during maintenance cannot silently create a locked task. Do not use `always`: it is for system/privileged apps and automatic locking conflicts with the explicit owner. `setLockTaskFeatures` controls system UI while locked, not re-entry; retain and verify the approved flags. Avoid `ActivityOptions.setLockTaskEnabled(true)` on HOME. [Manifest reference](https://developer.android.com/guide/topics/manifest/activity-element#lock), [lock-task guide](https://developer.android.com/work/dpc/dedicated-devices/lock-task-mode).
- Persist atomically before stopping: maintenance generation, fixed `elapsedRealtime()` deadline (10 minutes) and `Settings.Global.BOOT_COUNT`. Reject repeated exits and never extend the deadline. Revoke capture/input first. Stop only while the owner is resumed; confirm `NONE` before acknowledging exit. Failure or ambiguous state cancels maintenance and initiates recovery. An early `enter_kiosk` cancels the window and starts recovery under the policy table. Status reports observed lock state, maintenance and recovery failure; never claim locked from a request alone.
- Expiry schedules a persisted, wakeup recovery trigger; on delivery invalidate the window and request the owner in the foreground. Also reconcile on service start, activity create/resume, HOME entry, package replacement and boot after first unlock. Process death or app update cancels maintenance immediately on next execution; reboot or missing, malformed, unreadable or changed boot count fails closed. A destroyed activity cannot own a timer: the durable trigger and service reconcile independently. A wall-clock change cannot extend the window. Persist recovery-pending until `LOCKED` is observed; retry on each trigger and report failures when connected. Background activity launch and alarm delivery are platform-dependent: no promise of immediate re-entry without K11 evidence. If a launch is blocked, surface failure and require supervised local recovery; do not enable remote exit unless P3k proves the deadline on the deployed device.
- HOME remains this app's `LauncherActivity`. During a valid maintenance window HOME shows maintenance controls and does not launch or lock MainActivity automatically; it rechecks the deadline on create/resume and before actions. Outside that window it routes to MainActivity for recovery, does not start lock task itself, and does not offer Chrome or settings while recovery is pending. Back at WebView history root stays in the kiosk; it must not invoke the existing `exitToHome()` path. Remote Back remains confined to validated WebView history.

### §§5.5, 7/P3k, 7.1 — recovery checkpoint

- Boot remains credential-encrypted and after first unlock. Restore and verify DO policy, then reconcile and launch the owner; report blocked launch or failed lock. Update acceptance includes an in-place signed upgrade during maintenance, as well as the existing owner/key checks. P3k is the release gate for `EXIT_KIOSK_ENABLED`, independent of wipe.

## Acceptance tests:

- On API 35 and the provisioned K11, record build, DO, allowlist, resolved lock-task features and manifest. Start from HOME; verify MainActivity's root task starts `LOCKED`. Exit through the authorized path; verify only the resumed owner stops it, system state becomes `NONE`, and capture/input stop. Exercise HOME, Back, Wi-Fi and Chrome during maintenance; no automatic relock or accidental extension.
- With the tablet idle and another app foreground, allow expiry; record actual elapsed deadline, trigger delivery, foreground launch and `LOCKED`. Repeat with service/process killed, activity destroyed, reboot before expiry (unlock locally), and signed in-place update during maintenance. For each, verify reconciliation, owner task and observed `LOCKED`; test early enter, repeated exit, wall-clock change and invalid boot count. Confirm recovery failure is reported and local recovery works when launch or policy is deliberately blocked. No automatic exit enablement on partial success.
- Repeat HOME and Back after recovery; confirm HOME routes to the owner and no second locked task prevents exit. Verify `PINNED`, missing allowlist and locked keyguard never count as success. Record K11 timestamps, state observations and failures; emulator results do not replace K11 evidence.
