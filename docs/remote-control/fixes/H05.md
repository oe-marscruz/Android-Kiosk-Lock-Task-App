# H05 — Owner task and bounded maintenance

Replaces/amends: ARCHITECTURE.md v0.3 §§2.2 (Lock-task ownership), 4 (`exit_kiosk`, `enter_kiosk`, maintenance and recovery), 5.5 (boot), 7 (P3k, P4), 7.1 (upgrade acceptance), 9 (lock-task rollout and exit gate).

## Drop-in text

### §§2.2, 4 — task ownership

- P1 preserves the existing manifest behavior. P4 changes MainActivity, LauncherActivity and WifiSettingsActivity from `if_whitelisted` to `normal`, subject to the P4 gates below. MainActivity alone explicitly starts and stops lock task; no `ActivityOptions.setLockTaskEnabled(true)`. Preserve the existing DO allowlist and approved lock-task features.
- Give MainActivity a dedicated app-private task affinity and `singleTask` launch mode. HOME remains LauncherActivity; outside maintenance it explicitly launches MainActivity with `FLAG_ACTIVITY_NEW_TASK`, reusing its task. Do not use `MULTIPLE_TASK` or `NEW_DOCUMENT`. MainActivity must be task root (`isTaskRoot()`); route all lock transitions to its resumed instance. Boot after first unlock and package replacement reconcile durable state and use the same explicit launch and task reuse path. Do not assume an old task ID survives reboot, update, task removal or ID reuse.
- Establish ownership only on a controlled transition: while resumed, root, DO and allowlisted, keyguard unlocked, and global state `NONE`, record the current boot count and `getTaskId()`; call `startLockTask()` and require `LOCKED` immediately afterward with the same resumed root and task ID. Persist that identity and the successful transition atomically. `PINNED`, exceptions, pre-existing `LOCKED`, duplicate/unknown root, or changed identity are failures, not ownership. On resume recheck boot count, task ID, root, allowlist and `LOCKED`, and match the app's `ActivityManager.getAppTasks()` / `AppTask.getTaskInfo()` entry to that ID; missing or ambiguous evidence invalidates ownership. Global `LOCKED` alone never proves ownership. Public app-task APIs expose only the caller's tasks and do not identify the system locked task; this is a controlled-transition invariant, not a direct query of the locked task. If the invariant cannot be re-established, report recovery failure and require supervised recovery; never stop an unverified task. [AppTask](https://developer.android.com/reference/android/app/ActivityManager.AppTask), [lock task](https://developer.android.com/work/dpc/dedicated-devices/lock-task-mode), [Android 15 LockTaskController](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/android15-release/services/core/java/com/android/server/wm/LockTaskController.java).
- Before exit revoke capture and input; persist generation, boot count and fixed ten-minute `elapsedRealtime()` deadline. Reject repeated exits and do not extend the deadline. Schedule recovery successfully before the verified resumed owner calls `stopLockTask()`; require observed `NONE` before acknowledging. A scheduling or stop failure cancels exit and starts recovery; never acknowledge an ambiguous result. During a valid maintenance window every MainActivity `onResume` checks durable state first and must not call `startLockTask()`. HOME displays maintenance controls without auto-lock. Early `enter_kiosk` invalidates the window and initiates recovery. At expiry invalidate it before launching the owner; persist recovery-pending until the controlled owner transition succeeds. On process restart or package replacement cancel maintenance and reconcile immediately; on reboot, invalid boot count or unreadable state fail closed after first unlock. Do not claim automatic recovery if launch or locking fails.

### §§4, 5.5 — wakeup

- Use `AlarmManager.setExactAndAllowWhileIdle(ELAPSED_REALTIME_WAKEUP, deadline, immutable explicit broadcast PendingIntent)` addressed to a non-exported receiver, unique to the maintenance generation. Persist the pending generation before scheduling; serialize scheduling, stop and reconciliation. Check `canScheduleExactAlarms()`, then require the scheduling call to return normally before stop; catch failure and recheck permission/state before stopping. This is confirmation that the system accepted the request, not proof of future delivery: Android provides no public general query proving an individual alarm remains scheduled. Ignore stale generation deliveries. Alarm delivery can be delayed by idle quotas and does not itself prove a background activity launch or relock.
- API 35 permits this for a DO app when exact-alarm access or a real exemption applies; DO status alone is not an exact-alarm exemption. Declare `SCHEDULE_EXACT_ALARM`, verify special access or power-allowlist exemption on the deployed device; a fresh install targeting 33+ is not generally pre-granted. `USE_EXACT_ALARM` is restricted to qualifying alarm/calendar use cases and distribution policy; do not claim it for kiosk maintenance. If access is unavailable, scheduling throws, or K11 cannot demonstrate the bound, deny remote exit and remain locked; an inexact `setAndAllowWhileIdle` is useful only as a recovery backup, never authorization to exit. Reconcile on receiver, service/activity start, HOME, update and boot; an alarm may be removed on reboot or permission revocation. [AlarmManager](https://developer.android.com/reference/android/app/AlarmManager#setExactAndAllowWhileIdle(int,%20long,%20android.app.PendingIntent)), [exact alarm access](https://developer.android.com/about/versions/14/changes/schedule-exact-alarms), [Android 15 alarm service](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/android15-release/apex/jobscheduler/service/java/com/android/server/alarm/AlarmManagerService.java), [background launches](https://developer.android.com/guide/components/activities/secure-bal).

### §§7/P3k–P4, 7.1, 9 — release gates

- `EXIT_KIOSK_ENABLED` remains false until P3k records K11 evidence for the exact deployed build, DO policy and alarm access. Measure deadline, delivery, foregrounding and verified owner `LOCKED` with (1) another app foreground at expiry, (2) app process killed after exit, and (3) signed in-place update during maintenance. Update or restart must cancel the window and recover; a blocked launch or missed bound fails the gate. Repeat after relevant build, policy or platform changes. The alarm is not a guarantee of an exact deadline; if K11 cannot meet the ten-minute bound, keep exit disabled and use supervised local recovery.
- Before P4 switches the manifest, pass on K11: cold boot through first unlock to the verified owner; signed in-place upgrade with existing DO, keys and task state preserved or safely reconciled; and student HOME, WebView Back, Chrome and Settings/Wi-Fi paths with the existing allowlist and lock-task features. Confirm Chrome and Settings work as approved, no unintended unlocked or second locked task appears, and the owner can exit and recover. Block P4 on failure; emulator results do not substitute for K11.

## Acceptance tests:

- Exercise fresh HOME, repeated HOME, boot and upgrade; record task IDs, root status and observed lock state. Attempt duplicate/non-root and pre-existing `LOCKED` states; they must not establish ownership or authorize stop. Verify resume during maintenance never relocks.
- Deny exact alarm access and inject scheduling failure; exit remains locked and unacknowledged. Verify accepted generation, stale alarm rejection, fixed deadline, permission revocation, wall-clock changes and reboot reconciliation. Record actual K11 timing and recovery failures.
- Run all three P3k maintenance scenarios and P4 cold-boot, signed-upgrade, Chrome and Wi-Fi student paths above. Record build, policy, exact-alarm access, timestamps, foreground app, owner identity and result. Failure keeps the corresponding gate closed.
