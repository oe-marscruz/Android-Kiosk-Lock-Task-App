### ARCHITECTURE.md §2.1 Relay (`relay/`, new)

- Python 3.12 and aiohttp behind Caddy on OCI. One process handles fewer than 50 tablets. SQLite holds persistent registry, audit and session state; live sockets and attachments are process-local.
- **Lead is the integration owner** for `relay/app.py` (`create_app`), `relay/config.py`, versioned `relay/migrations/`, `relay/deploy/`, composition tests and integration of P2/P3. P2 owns `relay/auth/`, `relay/store.py` and the implementation of `relay/contracts.py`; P3 owns `relay/ws.py`, attachment state, bounded queues and routing. Changes to shared contracts require lead review. The lead composes the implementations once; neither worker creates a competing app factory or migration runner.
- `create_app(config: RelayConfig) -> aiohttp.web.Application` validates config, applies migrations before accepting traffic, constructs P2 services and injects them into P3 routes. Failed validation or migration prevents startup. Migration versions are ordered, recorded in SQLite and applied transactionally where SQLite permits; back up the database before upgrade and test upgrade from the previous released version.
- Config is loaded from environment and a config file, including `OIDC_ISSUER`, `OIDC_CLIENT_ID`, `OIDC_CLIENT_SECRET`, role mappings and `PUBLIC_BASE_URL`. Secrets stay on the server. Trial and CU Duo use the same code and contract with different configuration; never commit secrets.
- `relay/contracts.py` is the shared typed boundary. These are project interfaces, not library APIs; domain values are immutable records, identifiers are opaque strings, times are UTC, and methods are asynchronous. Implementations fail closed on invalid, expired or revoked credentials. Denials use the frozen error envelope; no exception text or secret crosses the boundary.

```python
from dataclasses import dataclass
from datetime import datetime
from typing import Protocol

@dataclass(frozen=True)
class Principal:
    issuer: str
    subject: str

@dataclass(frozen=True)
class StaffSession:
    session_id: str
    principal: Principal
    expires_at: datetime

@dataclass(frozen=True)
class DeviceIdentity:
    device_id: str

@dataclass(frozen=True)
class Decision:
    allowed: bool
    error_code: str | None

@dataclass(frozen=True)
class AuditEvent:
    principal: Principal | None
    device_id: str | None
    action: str
    outcome: str
    occurred_at: datetime

class SecurityServices(Protocol):
    async def authenticate_staff(self, token: str) -> StaffSession: ...
    async def authenticate_device(self, device_id: str, transcript: bytes, signature: bytes) -> DeviceIdentity: ...
    async def authorize(self, session: StaffSession, device_id: str | None, action: str) -> Decision: ...
    async def revoke_session(self, session_id: str) -> None: ...
    async def revoke_device(self, device_id: str) -> None: ...
    async def audit(self, event: AuditEvent) -> None: ...

class ConnectionCloser(Protocol):
    async def close_session(self, session_id: str) -> None: ...
    async def close_device(self, device_id: str) -> None: ...
```

- P2 validates staff sessions and socket-bound device proofs and owns authorization, durable revocation and audit. P3 calls these services before routing and on continuing session validity; it supplies `ConnectionCloser` to close affected sockets and attachments on revocation. Revocation completes only after persistent invalidation and closure have succeeded; reconnects remain denied even if closure fails. P2 and P3 agree integration details at contract freeze, including freshness and role-change enforcement. Enrollment and browser login remain P2 HTTP endpoints, not WSS routing interfaces.
- `relay/deploy/` contains the systemd unit, environment/config examples and Caddyfile. aiohttp binds only `127.0.0.1` on a configured port; Caddy alone exposes HTTPS/WSS and proxies to loopback. Protect configuration and secret files with service-account permissions. Verify from a separate host that public HTTPS and WSS work, the backend port is unreachable, and expiry and revocation terminate live access. Do not log credentials or frames.

### ARCHITECTURE.md §4 addition — Schema freeze

- The lead owns `docs/remote-control/protocol/v1.schema.json` and accompanying `docs/remote-control/protocol/v1.md` for binary framing and semantics. Before P2/P3 start in parallel, reconcile F01/F02/F06, freeze the versioned schema, operation and error registries, authentication and lifecycle rules, and checked-in valid/invalid examples. Both workers review the same commit; the lead records its commit ID in HANDOFF. Changes after freeze require lead approval, coordinated consumers and fixtures; incompatible changes require a new protocol version. CI validates fixtures and rejects unregistered types/codes. Unknown versions, message types and codes have explicit documented handling.
- JSON failures use the common envelope `{"v":1,"type":"error","id":"<request-id or null>","error":{"code":"<stable-code>"}}`. `id` correlates a request when available; null denotes an uncorrelated connection error. Codes and their retry/close semantics are defined in the frozen registry, not by exception strings. Never include secrets, raw URLs or stack traces. Binary frame layout is versioned and documented alongside the schema.
